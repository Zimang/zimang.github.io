          本章涵盖内容

          1. 使用 ref 关键字为变量起别名
          2. 使用引用返回（ref returns）返回变量
          3. 使用 in 参数高效传递参数

          5. 以 in 或 ref 目标为目标的扩展方法
          6. 类似引用的结构体（Ref-like structs）和 Span<T>

          当 C# 7.0 发布时，有几个功能让我觉得有点奇怪：引用局部变量（ref locals）和引用返回（ref returns）。我有点怀疑有多少开发人员会需要它们，因为它们似乎针对涉及大型值类型的场景，而这种情况很少见。我的预期是只有近乎实时的服务和游戏会觉得这些功能有用。

          C# 7.2 带来了另一批与引用相关的功能：in 参数、只读引用局部变量和返回、只读结构体以及类似引用的结构体。这些是对 7.0 功能的补充，但似乎仍然是为了少数用户的利益而使语言变得更加复杂。

          我现在确信，尽管许多开发人员可能不会在他们的项目中直接看到更多基于引用的代码，但他们将因为框架中提供了更高效的功能而享受到这些功能存在的好处。在撰写本文时，要确切地说这将被证明有多么革命性还为时过早，但我认为它很可能意义重大。

          性能通常以牺牲可读性为代价。我仍然认为本章描述的许多功能就是这种情况；我预计它们会在性能已知足够重要、值得付出可读性代价的情况下被谨慎使用。然而，所有这些功能所带来的框架变革则是另一回事。它们应该能够相当容易地减少对象分配，节省内存和垃圾回收器的工作，而不会使您的代码更难阅读。

          我提出所有这些是因为您可能会有类似的反应。在阅读本章时，完全有理由决定尝试避免使用这里的大多数语言功能。但我敦促您坚持读到最后，以了解与框架相关的好处。关于类似引用结构体的最后一部分介绍了 Span<T>。关于 Span 可以说的内容远比我在这本书中有空间写的要多，但我预计 Span 和相关类型将成为未来开发人员工具箱的重要组成部分。

          在本章中，我会提到某个功能仅在 C# 7 的某个小版本中可用。与其他小版本功能一样，这意味着如果您使用的是 C# 7 编译器，只有通过适当的项目设置指定语言版本，您才能利用这些功能。我建议您对与引用相关的功能采取全有或全无的方法：要么使用所有功能，并使用适当的设置来允许这样做，要么一个都不用。仅使用 C# 7.0 中的功能可能会不太令人满意。说了这么多，让我们从回顾早期 C# 版本中 ref 关键字的使用开始。

          回顾：关于 ref 你知道什么？#

          为了理解 C# 7 中与引用相关的功能，您需要牢固掌握 ref 参数在 C# 6 及更早版本中是如何工作的。而这又需要牢固掌握变量与其值之间的区别。

          图 13.1 将变量表示为一张纸

          当变量类型是引用类型时，写在纸上的值从来不是对象；它总是一个对象引用。对象引用只是一种导航到对象的方式，就像街道地址是导航到建筑物的一种方式一样。两张纸上写有相同的地址，指的是同一栋建筑，就像两个具有相同引用值的变量指向同一个对象一样。

          提示 ref 关键字和对象引用是不同的概念。它们当然存在相似之处，但您需要区分它们。例如，按值传递对象引用与按引用传递变量是不同的。在本节中，我通过使用“对象引用”而不仅仅是“引用”来强调这种区别。

          重要的是，当赋值将一个变量的值复制到另一个变量时，复制的真的只是值；两张纸保持独立，以后对任一变量的更改都不会改变另一个。图 13.2 说明了这个概念。

          这种值复制正是调用方法时值参数（value parameter）所发生的情况；方法参数的值被复制到一张新的纸上——即参数，如图 13.3 所示。参数不一定是变量；它可以是任何适当类型的表达式。

          引用参数的行为则不同，如图 13.4 所示。引用参数不是充当一张新纸，而是要求调用者提供一张现有的纸，而不仅仅是一个初始值。您可以把它看作一张写有两个名字的纸：调用代码用来标识它的名字和参数名。

          如果方法修改了 ref 参数的值，从而改变了纸上写的内容，那么当方法返回时，调用者可以看到这个变化，因为它是在原始纸张上。

          注意 关于 ref 参数和变量有不同的思考方式。您可能会读到其他作者将 ref 参数视为完全独立的变量，只是具有一个自动的间接层，以便对 ref 参数的任何访问都首先遵循这个间接层。这更接近 IL 的表示方式，但我觉得它帮助不大。

          并没有要求每个 ref 参数必须使用不同的纸。下面的清单提供了一个有点极端的例子，但它有助于在继续学习引用局部变量之前检查您的理解。

          清单 13.1 为多个 ref 参数使用同一个变量

          static void Main()
{
    int x = 5;
    IncrementAndDouble(ref x, ref x);
    Console.WriteLine(x);
}
static void IncrementAndDouble(ref int p1, ref int p2)
{
    p1++;
    p2 *= 2;
}

          这里的输出是 12：x, p1, p2 都代表同一张纸。它开始的值是 5；p1++ 将其增加到 6，p2 *= 2 将其翻倍到 12。图 13.5 显示了所涉及变量的图形表示。

          描述这种情况的常用方式是别名：在前面的例子中，变量 x、p1 和 p2 都是同一存储位置的别名。它们是访问同一块内存的不同方式。

          如果这看起来冗长且老生常谈，敬请见谅。您现在可以继续学习 C# 7 真正的新功能了。有了将变量视为纸张的思维模型，理解新功能将会容易得多。

          本节通过“纸张”隐喻清晰地解释了变量、值、引用和 ref 参数的核心概念。其关键在于区分变量本身与变量所持有的值。对于引用类型，变量存储的是对象引用（即“地址”），而非对象本身。ref 参数的本质是传递变量的别名，使形参和实参指向同一存储位置，从而实现双向数据传递。这与按值传递对象引用有根本区别：后者复制的是引用（地址），但调用方和受调方仍持有两个独立的变量（即两张“纸”），只是它们指向同一个对象。理解这一基础对掌握后续 ref 返回、in 参数等高级特性至关重要，因为它们都建立在“别名”这一核心思想上，旨在避免不必要的值复制，提升性能。

          引用局部变量与引用返回#

          许多与引用相关的 C# 7 功能是相互关联的，这使得当你一次只看到一个功能时，更难理解它们的好处。在我描述这些功能时，示例将比平时更加刻意，因为它们试图一次只演示一个要点。你将看到的头两个功能是在 C# 7.0 中引入的，尽管它们在 C# 7.2 中得到了增强。首先是引用局部变量。

          引用局部变量#

          让我们继续之前的比喻：引用参数允许一张纸在两个方法中的变量之间共享。调用者使用的同一张纸就是方法用于参数的那张纸。引用局部变量将这个想法更进一步，允许你声明一个新的局部变量，与现有变量共享同一张纸。

          下面的清单展示了一个简单的例子，通过不同的变量递增两次，然后显示结果。注意，你必须在声明和初始化表达式中都使用 ref 关键字。

          清单 13.2 通过两个变量递增两次

          int x = 10;
ref int y = ref x;
x++;
y++;
Console.WriteLine(x);

          这将打印 12，就像你将 x 递增了两次一样。

          任何被归类为变量的适当类型的表达式都可以用于初始化引用局部变量，包括数组元素。如果你有一个大型可变值类型的数组，这可以避免不必要的复制操作，以便进行多次修改。下面的清单创建了一个元组数组，然后在没有复制的情况下修改每个数组元素内的两个项。

          清单 13.3 使用引用局部变量修改数组元素

          var array = new (int x, int y)[10];
for (int i = 0; i < array.Length; i++)
{
    array[i] = (i, i);  //将数组初始化为 (0, 0)、(1, 1) 等
}
for (int i = 0; i < array.Length; i++)
{
    ref var element = ref array[i];  //对数组的每个元素，递增 x 并加倍 y
    element.x++;
    element.y *= 2;
}

          在没有引用局部变量之前，修改数组有两种替代方案。你可以使用多个数组访问表达式，如下所示：

          for (int i = 0; i < array.Length; i++)
{
    array[i].x++;
    array[i].y *= 2;
}

          或者，你可以将整个元组从数组中复制出来，修改它，然后再复制回去：

          for (int i = 0; i < array.Length; i++)
{
    var tuple = array[i];
    tuple.x++;
    tuple.y *= 2;
    array[i] = tuple;
}

          这两种方法都不特别吸引人。引用局部变量的方法表达了我们的目标：在循环体中，将数组元素当作普通变量来处理。

          引用局部变量也可以与字段一起使用。静态字段的行为是可预测的，但实例字段的行为可能会让你惊讶。考虑下面的清单，它通过一个变量（obj）创建了一个引用局部变量来别名一个实例中的字段，然后将 obj 的值更改为引用另一个实例。

          清单 13.4 使用引用局部变量别名特定对象的字段

          class RefLocalField
{
    private int value;
    static void Main()
    {
        var obj = new RefLocalField();  
        ref int tmp = ref obj.value;
        tmp = 10;
        Console.WriteLine(obj.value);
        obj = new RefLocalField();
        Console.WriteLine(tmp);
        Console.WriteLine(obj.value);
    }
}

          输出如下：

          10
10
0

          可能令人惊讶的是中间那一行。它表明使用 tmp 并不等同于每次使用 obj.value。相反，tmp 充当了在初始化时表示为 obj.value 的字段的别名。图 13.6 显示了 Main 方法结束时涉及的变量和对象的快照。

          由此推论，tmp 变量将阻止第一个实例被垃圾回收，直到方法中最后一次使用 tmp 之后。类似地，为数组元素使用引用局部变量会阻止包含该元素的数组被垃圾回收。

          注意 引用对象内字段或数组元素的引用变量会使垃圾回收器的工作变得更加困难。它必须计算出变量是哪个对象的一部分，并保持该对象存活。常规的对象引用更简单，因为它们直接标识所涉及的对象。每个引用对象中字段的引用变量都会在垃圾回收器维护的数据结构中引入一个内部指针。同时存在大量这样的指针会很昂贵，但引用变量只能出现在栈上，这使得不太可能出现足够多的情况导致性能问题。

          引用局部变量的使用确实有一些限制。其中大多数是显而易见的，不会妨碍你，但值得了解它们，这样你就不会尝试去绕过它们。

          初始化：一次性，仅在声明时（C# 7.3 之前） 引用局部变量必须在声明时初始化。例如，以下代码无效：

          int x = 10;
ref int invalid;
invalid = ref int x;

          同样，无法更改引用局部变量以别名另一个变量。（用我们的模型术语来说，你不能擦掉名字然后把它写在另一张纸上。）当然，同一个变量可以有效地声明多次；例如，在清单 13.3 中，你在循环中声明了 element 变量：

          for (int i = 0; i < array.Length; i++)
{
    ref var element = ref array[i];
    ...
}

          在循环的每次迭代中，element 将别名不同的数组元素。但这没关系，因为每次迭代它实际上都是一个新的变量。

          用于初始化引用局部变量的变量也必须明确赋值。你可能期望变量共享明确赋值状态，但语言设计者没有让明确赋值规则更加复杂，而是确保引用局部变量总是明确赋值的。下面是一个例子：

          int x;
ref int y = ref x;
x = 10;
Console.WriteLine(y);

          无效，因为 x 未明确赋值

          这段代码直到所有内容都明确赋值后才尝试读取任何变量，但它仍然无效。

          C# 7.3 取消了对重新赋值的限制，但引用局部变量仍然必须在声明时使用明确赋值的变量进行初始化。例如：

          int x = 10;
int y = 20;
ref int r = ref x;
r++;
r = ref y; // 仅在 C# 7.3 中有效
r++;
Console.WriteLine($"x={x}; y={y}");

          打印 x = 11, y = 21

          我敦促在使用此功能时保持一定程度的谨慎。如果你需要同一个引用变量在方法过程中引用不同的变量，我建议至少尝试将方法重构得更简单。

          没有引用字段，或生存期超出方法调用的局部变量 尽管引用局部变量可以使用字段进行初始化，但你不能使用 ref 声明字段。这是防止引用变量作为生存期更短的另一个变量的别名的一个方面。如果你可以创建一个对象，其字段别名了方法中的局部变量，那将会产生问题；方法返回后，该字段会发生什么？

          对生存期的同样担忧在三种情况下扩展到局部变量： 迭代器块不能包含引用局部变量。 异步方法不能包含引用局部变量。 引用局部变量不能被匿名方法或局部方法捕获。（局部方法在第14章描述。）

          这些都是局部变量的生存期可能超出原始方法调用的情况。有时，编译器可能能够证明这不会导致问题，但为了简单起见，选择了语言规则。（一个简单的例子是只被包含方法调用而不是用于方法组转换的局部方法。）

          不能引用只读变量 C# 7.0 中引入的任何引用局部变量都是可写的；你可以在纸上写一个新值。如果你试图使用不可写的纸来初始化引用局部变量，那就会产生问题。考虑这个试图违反 readonly 修饰符的例子：

          class MixedVariables
{
    private int writableField;
    private readonly int readonlyField;
    public void TryIncrementBoth()
    {
        ref int x = ref writableField; //别名可写字段
        ref int y = ref readonlyField; //尝试别名只读字段
        //递增两个变量
        x++;
        y++;
    }
}

          如果这是有效的，我们多年来建立的关于只读字段的所有推理都将丢失。幸运的是，情况并非如此；编译器会阻止对 y 的赋值，就像它会阻止对 readonlyField 的任何直接修改一样。但是这段代码在 MixedVariables 类的构造函数中是有效的，因为在这种情况下，你也可以直接写入 readonlyField。简而言之，你只能以别名在其他情况下可以写入的变量的方式来初始化引用局部变量。这与从 C# 1.0 开始将字段用作引用参数参数的行为相匹配。

          如果你想利用引用局部变量的共享方面而不涉及可写方面，这个限制可能会令人沮丧。在 C# 7.0 中，这是一个问题；但你将在 13.2.4 节中看到，C# 7.2 提供了一个解决方案。

          类型：只允许恒等转换 引用局部变量的类型必须与它正在初始化的变量的类型相同，或者两种类型之间必须存在恒等转换。任何其他转换——甚至是在许多其他场景中允许的引用转换——都是不够的。下面的清单展示了一个使用基于元组的恒等转换的引用局部变量声明的例子，你在第11章学过。

          注意 有关恒等转换的提醒，请参见第11.3.3节。

          清单 13.5 引用局部变量声明中的恒等转换

          (int x, int y) tuple1 = (10, 20);
ref (int a, int b) tuple2 = ref tuple1;
tuple2.a = 30;
Console.WriteLine(tuple1.x);

          这将打印 30，因为 tuple1 和 tuple2 共享相同的存储位置；tuple1.x 和 tuple2.a 彼此等价，tuple1.y 和 tuple2.b 也是如此。

          在本节中，你已经了解了从局部变量、字段和数组元素初始化引用局部变量。在 C# 7 中，有一种新表达式被归类为变量：通过引用返回方法返回的变量。

          引用返回#

          在某些方面，理解引用返回应该很容易。使用我们之前的模型，它是方法可以返回一张纸而不是一个值的想法。你需要在返回类型和任何返回语句中添加 ref 关键字。调用代码通常也会声明一个引用局部变量来接收返回值。这意味着你必须在代码中相当自由地使用 ref 关键字，以明确你试图做什么。下面的清单展示了引用返回的最简单可能用法；RefReturn 方法返回传递给它的任何变量。

          清单 13.6 最简单的引用返回演示

          static void Main()
{
    int x = 10;
    ref int y = ref RefReturn(ref x);
    y++;
    Console.WriteLine(x);
}
static ref int RefReturn(ref int p)
{
    return ref p;
}

          这将打印 11，因为 x 和 y 在同一张纸上，就像你写了

          ref int y = ref x;

          该方法本质上是一个恒等函数，只是为了展示语法。它本可以写成一个表达式体方法，但我想让返回部分清晰明了。

          到目前为止，一切都很简单，但很多细节会妨碍理解，主要是因为编译器确保返回的任何一张纸在方法完成返回时仍然存在。它不能是方法中创建的纸。

          用实现术语来说，方法不能返回刚刚在栈上创建的存储位置，因为当栈弹出时，存储位置将不再有效。在描述 C# 语言如何工作时，Eric Lippert 喜欢说栈是一个实现细节（参见 http://mng.bz/oVvZ）。在这种情况下，这是一个泄漏到语言中的实现细节。这些限制与禁止引用字段的原因相同，所以如果你觉得你理解其中一个，你可以将相同的逻辑应用到另一个。

          我不会详述每一种可以使用引用返回和不能使用引用返回的变量，但这里有一些最常见的例子：

          有效的

          1. ref 或 out 参数
          2. 引用类型的字段
          3. 结构体的字段，其中结构体变量是 ref 或 out 参数
          4. 数组元素

          无效的

          1. 在方法中声明的局部变量（包括值参数）
          2. 在方法中声明的结构体变量的字段

          除了这些关于什么可以返回和什么不能返回的限制之外，引用返回在异步方法和迭代器块中完全无效。与指针类型类似，你不能在类型参数中使用 ref 修饰符，尽管它可以出现在接口和委托声明中。例如，这完全有效：

          delegate ref int RefFuncInt32();

          但你不能通过尝试引用 Func<ref int> 来获得相同的结果。

          引用返回不一定与引用局部变量一起使用。如果你想对结果执行单个操作，可以直接进行。下面的清单使用与清单 13.6 相同的代码展示了这一点，但没有引用局部变量。

          清单 13.7 直接递增引用返回的结果

          static void Main()
{
    int x = 10;
    RefReturn(ref x)++;
    Console.WriteLine(x);
}
static ref int RefReturn(ref int p)
{
    return ref p;
}

          直接递增返回的变量

          同样，这等价于递增 x，所以输出是 11。除了修改结果变量之外，你还可以将它用作另一个方法的引用参数。让我们已经纯粹演示性的例子变得更加愚蠢，你可以用自身的结果（两次）调用 RefReturn：

          RefReturn(ref RefReturn(ref RefReturn(ref x)))++;

          引用返回对索引器和方法都有效。这最常用于通过引用返回数组元素，如下面的清单所示。

          清单 13.8 通过引用返回数组元素的引用返回索引器

          class ArrayHolder
{
    private readonly int[] array = new int[10];
    public ref int this[int index] => ref array[index];  //索引器通过引用返回数组元素
}
static void Main()
{
    ArrayHolder holder = new ArrayHolder();
    ref int x = ref holder[0]; //声明两个引用局部变量指向同一个数组元素
    ref int y = ref holder[0];
    x = 20;  //通过 x 更改数组元素值
    Console.WriteLine(y);  //通过 y 观察变化
}

          你现在已经涵盖了 C# 7.0 中的所有新功能，但后来的小版本扩展了与引用相关的功能集。第一个功能是我在撰写本章初稿时非常沮丧的一个：缺乏对条件 ?: 运算符的支持。

          条件 ?: 运算符和引用值（C# 7.2） 条件 ?: 运算符自 C# 1.0 以来就一直存在，并且在其他语言中也很熟悉：

          condition ? expression1 : expression2

          它计算其第一个操作数（条件），然后计算第二个或第三个操作数以提供整体结果。很自然地想要用引用值实现同样的事情，根据条件选择一个或另一个变量。

          在 C# 7.0 中，这是不可行的，但在 C# 7.2 中是可以的。条件运算符可以将引用值用于第二个和第三个操作数，此时条件运算符的结果也是一个可以与 ref 修饰符一起使用的变量。例如，下面的清单展示了一个方法，它计算序列中的偶数和奇数值，并将结果作为元组返回。

          清单 13.9 计算序列中的偶数和奇数元素

          static (int even, int odd) CountEvenAndOdd(IEnumerable<int> values)
{
    var result = (even: 0, odd: 0);
    foreach (var value in values)
    {
        ref int counter = ref (value & 1) == 0 ?  //选择适当的变量进行递增
            ref result.even : ref result.odd;
        counter++;  //递增它
    }
    return result;
}

          这里使用元组有些巧合，尽管它有助于证明元组可变的用处。这个增加使得语言感觉更加一致。条件运算符的结果可以用作引用参数的参数，赋值给引用局部变量，或用于引用返回。一切都很好地呈现出来。

          下一个 C# 7.2 功能解决了你在 13.2.1 节讨论引用局部变量限制时看过的一个问题：如何获取只读变量的引用？

          只读引用（C# 7.2）#

          到目前为止，你一直别名的所有变量都是可写的。在 C# 7.0 中，这是所有可用的。但这在两种并行的场景中是不够的： 你可能为了效率而想要别名一个只读字段，以避免复制。 你可能只想允许通过引用变量进行只读访问。

          C# 7.2 中引入的 ref readonly 解决了这两种场景。引用局部变量和引用返回都可以用 readonly 修饰符声明，结果是只读的，就像只读字段一样。你不能为变量分配新值，如果它是结构体类型，你不能修改任何字段或调用属性设置器。

          提示 考虑到使用 ref readonly 的原因之一是为了避免复制，你可能惊讶地听说有时它会产生相反的效果。你将在 13.4 节详细讨论这一点。在没有阅读那一节之前，不要开始在生产代码中使用 ref readonly！

          你可以放置修饰符的两个地方一起工作：如果你调用一个具有 ref readonly 返回的方法或索引器，并希望将结果存储在局部变量中，它也必须是一个 ref readonly 局部变量。下面的清单展示了只读方面如何链接在一起。

          清单 13.10 只读引用返回和局部变量

          static readonly int field = DateTime.UtcNow.Second;
static ref readonly int GetFieldAlias() => ref field;
static void Main()
{
    ref readonly int local = ref GetFieldAlias();
    Console.WriteLine(local);
}

          用任意值初始化只读字段 返回字段的只读别名 使用方法初始化只读引用局部变量

          这也适用于索引器，它允许不可变集合直接暴露其数据，而无需任何复制，但没有任何内存被更改的风险。注意，你可以返回 ref readonly 而基础变量不是只读的，这提供了数组的只读视图，很像 ReadOnlyCollection 对任意集合所做的，但具有无复制的读取访问。下面的清单展示了这个想法的简单实现。

          清单 13.11 具有无复制读取的数组只读视图

          class ReadOnlyArrayView<T>
{
    private readonly T[] values;
    public ReadOnlyArrayView(T[] values) =>  //复制数组引用而不克隆内容
        this.values = values;
    public ref readonly T this[int index] =>  //返回数组元素的只读别名
        ref values[index];
}
...
static void Main()
{
    var array = new int[] { 10, 20, 30 };
    var view = new ReadOnlyArrayView<int>(array);
    ref readonly int element = ref view[0];
    Console.WriteLine(element);  //对数组的修改通过局部变量可见
    array[0] = 100;
    Console.WriteLine(element);
}

          这个例子在效率增益方面并不令人信服，因为 int 已经是一个小类型，但在使用较大的结构体以避免过多的堆分配和垃圾收集的场景中，好处可能很显著。

          实现细节 在 IL 中，ref readonly 方法被实现为常规的引用返回方法（返回类型是按引用类型），但应用了来自 System.Runtime.InteropServices 命名空间的 [InAttribute]。这个属性又在 IL 中用 modreq 修饰符指定：如果编译器不知道 InAttribute，它应该拒绝对该方法的任何调用。这是一种安全机制，防止误用方法的返回值。想象一个 C# 7.0 编译器（知道引用返回但不知道只读引用返回）试图从另一个程序集调用一个返回 ref readonly 的方法。它可能允许调用者将结果存储在可写的引用局部变量中，然后修改它，从而违反 ref readonly 返回的意图。

          除非 InAttribute 对编译器可用，否则你不能声明 ref readonly 返回方法。这很少成为问题，因为它自 .NET 1.1 以来就在桌面框架中，并且在 .NET Standard 1.1 中。如果你绝对必须，你可以在正确的命名空间中声明自己的属性，编译器将使用它。

          正如你所看到的，readonly 修饰符可以应用于局部变量和返回类型，但参数呢？如果你有一个 ref readonly 局部变量，并且想在不复制值的情况下将它传递给一个方法，你有什么选择？你可能期望答案再次是 readonly 修饰符，只是应用于参数，但现实略有不同，你将在下一节中看到。

          本节深入介绍了 C# 7.0 引入的 ref 局部变量和 ref 返回，以及 C# 7.2 引入的 ref readonly 和条件运算符对 ref 的支持。这些特性的核心目的是通过避免不必要的值复制来提高性能，特别是在处理大型结构体时。它们允许直接别名现有变量（包括数组元素、字段等），使多个名称指向同一内存位置，从而实现对数据的直接操作或只读访问。

          然而，这些特性也带来了复杂性：它们有严格的限制（如生存期管理、不能用于异步上下文等），并且可能影响垃圾回收。ref readonly 在提供只读视图的同时，有时反而可能导致复制（防御性复制），因此需要谨慎使用。

          总体而言，这些特性主要用于性能关键场景，通常被框架（如 Span<T>）内部使用，以提供高效的内存访问。对于大多数应用开发，应优先考虑代码清晰度，仅在确有必要时使用这些高级特性。

          in 参数（C# 7.2）#

          C# 7.2 添加了 in 作为参数的新修饰符，其风格与 ref 或 out 类似，但意图不同。当参数有 in 修饰符时，意图是方法不会更改参数值，因此可以通过引用传递变量以避免复制。在方法内部，in 参数的行为类似于 ref readonly 局部变量。它仍然是调用者传递的存储位置的别名，因此方法不修改值很重要；调用者会看到这种更改，这与它作为 in 参数的本意相悖。

          in 参数与 ref 或 out 参数有一个很大的区别：调用者不必为参数指定 in 修饰符。如果缺少 in 修饰符，编译器将通过引用传递参数（如果参数是变量），但如果需要，则会复制值作为隐藏的局部变量并通过引用传递该副本。如果调用者明确指定 in 修饰符，则仅当参数可以直接通过引用传递时，调用才有效。下面的清单显示了所有可能性。

          清单 13.12 为 in 参数传递参数的有效和无效可能性

          static void PrintDateTime(in DateTime value)  //声明带有 in 参数的方法
{
    string text = value.ToString(
        "yyyy-MM-dd'T'HH:mm:ss",
        CultureInfo.InvariantCulture);
    Console.WriteLine(text);
}
static void Main()
{
    DateTime start = DateTime.UtcNow;
    PrintDateTime(start); //变量隐式通过引用传递
    PrintDateTime(in start);  //变量显式通过引用传递（由于 in 修饰符）
    PrintDateTime(start.AddMinutes(1)); //结果被复制到隐藏的局部变量，该变量通过引用传递
    PrintDateTime(in start.AddMinutes(1)); //编译时错误：参数无法通过引用传递
}

          在生成的 IL 中，该参数等同于用 System.Runtime.CompilerServices 命名空间中的 [IsReadOnlyAttribute] 修饰的 ref 参数。这个属性的引入比 InAttribute 晚得多；它位于 .NET 4.7.1 中，但甚至不在 .NET Standard 2.0 中。如果必须添加依赖项或自己声明该属性会很烦人，因此如果编译器无法以其他方式获取该属性，它会在你的程序集中自动生成该属性。

          该属性在 IL 中没有 modreq 修饰符；任何不理解 IsReadOnlyAttribute 的 C# 编译器都会将其视为常规的 ref 参数。（CLR 也不需要知道该属性。）任何使用较新版本编译器重新编译的调用者将突然无法编译，因为它们现在需要 in 修饰符而不是 ref 修饰符。这引出了关于向后兼容性的更大话题。

          兼容性注意事项#

          调用站点可选 in 修饰符的方式导致了一个有趣的向后兼容情况。将方法参数从值参数（默认，无修饰符）更改为 in 参数总是源兼容的（你应该总是能够在不更改调用代码的情况下重新编译），但永远不是二进制兼容的（任何已编译的调用该方法的现有程序集将在执行时失败）。确切含义将取决于你的情况。假设你想为已发布的程序集将方法参数更改为 in 参数：

          • 如果你的方法可以被你无法控制的调用者访问（例如，如果你正在向 NuGet 发布库），这是一个破坏性变更，应像对待任何其他破坏性变更一样处理。
          • 如果你的代码只能被那些在使用新版本程序集时肯定会重新编译的调用者访问（即使你无法更改该调用代码），那么这不会破坏那些调用者。
          • 如果你的方法仅在你的程序集内部，你无需担心二进制兼容性，因为所有调用者无论如何都会被重新编译。

          还存在另一种不太可能的情况：如果你有一个纯粹为了避免复制而带有 ref 参数的方法（你从未在方法中修改参数），将其更改为 in 参数总是二进制兼容的，但永远不是源兼容的。这与将值参数更改为 in 参数完全相反。

          所有这一切都假设使用 in 参数不会破坏方法本身的语义。这并不总是一个有效的假设；让我们看看原因。

          in 参数令人惊讶的可变性：外部更改#

          到目前为止，听起来如果你不在方法内修改参数，将其设为 in 参数是安全的。但事实并非如此，这是一个危险的预期。编译器阻止方法修改参数，但它无法阻止其他代码修改它。你需要记住，in 参数是存储位置的别名，其他代码可能能够修改该存储位置。让我们先看一个简单的例子，这可能看起来非常明显。

          清单 13.13 in 参数和值参数在副作用面前的差异

          static void InParameter(in int p, Action action)
{
    Console.WriteLine("Start of InParameter method");
    Console.WriteLine($"p = {p}");
    action();
    Console.WriteLine($"p = {p}");
}
static void ValueParameter(int p, Action action)
{
    Console.WriteLine("Start of ValueParameter method");
    Console.WriteLine($"p = {p}");
    action();
    Console.WriteLine($"p = {p}");
}
static void Main()
{
    int x = 10;
    InParameter(x, () => x++);
    ValueParameter(x, () => x++);
}

          除了显示的日志消息和参数的性质外，前两个方法是相同的。在 Main 方法中，你以相同的方式调用这两个方法，传递一个初始值为 10 的局部变量作为参数，以及一个递增该变量的操作。输出显示了语义上的差异：

          Start of InParameter method
p = 10
p = 11
Start of ValueParameter method
p = 10
p = 10

          如你所见，InParameter 方法能够观察到调用 action() 引起的变化；ValueParameter 方法则不能。这并不奇怪；in 参数旨在共享存储位置，而值参数旨在复制。

          问题是，尽管在这个特定情况下很明显，因为代码很少，但在其他例子中可能不明显。例如，in 参数可能恰好是同一类中字段的别名。在这种情况下，对字段的任何修改，无论是在方法中直接进行还是由方法调用的其他代码进行，都将通过参数可见。这在调用代码或方法本身中都不明显。当涉及多个线程时，更难预测会发生什么。

          我在这里故意有点危言耸听，但我认为这是一个真正的问题。我们习惯于通过指定参数和参数上的修饰符来强调使用 ref 参数可能带来的这种行为。此外，ref 修饰符感觉隐式地关注参数中更改的可见性，而 in 修饰符是关于不更改参数的。在 13.3.4 节中，我将给出更多关于使用 in 参数的指导，但目前你应该意识到参数值意外更改的潜在风险。

          使用 in 参数重载#

          我还没有触及的一个方面是方法重载：如果你想要两个具有相同名称和相同参数类型的方法，但在一种情况下参数是 in 参数，在第二种方法中不是，会发生什么？

          请记住，就 CLR 而言，这只是另一个 ref 参数。你不能仅通过更改 ref、out 和 in 修饰符来重载方法；它们对 CLR 来说看起来是一样的。但你可以使用常规的值参数重载一个 in 参数：

          void Method(int x) { ... }
void Method(in int x) { ... }

          重载解析中的新决胜规则使得对于没有 in 修饰符的参数，具有值参数的方法更好：

          int x = 5;
Method(5);       // 调用第一个方法
Method(x);       // 调用第一个方法
Method(in x);    // 由于 in 修饰符，调用第二个方法

          这些规则允许你为现有方法名称添加重载，如果现有方法具有值参数而新方法具有 in 参数，则兼容性方面不会有太多顾虑。

          关于 in 参数的指导#

          完全披露：我还没有在实际代码中使用过 in 参数。这里的指导是推测性的。

          首先要注意的是，in 参数旨在提高性能。作为一个一般原则，我不会开始对你的代码进行任何更改以提高性能，除非你已经以有意义和可重复的方式测量了性能并设定了目标。如果不小心，你可能会以优化的名义使代码复杂化，结果却发现即使你大幅提高了一两个方法的性能，这些方法也不在应用程序的关键路径上。你的具体目标将取决于你编写的代码类型（游戏、Web 应用程序、库、IoT 应用程序或其他），但仔细的测量很重要。对于微基准测试，我推荐 BenchmarkDotNet 项目。

          in 参数的好处在于减少需要复制的数据量。如果你只使用引用类型或小型结构体，可能根本没有任何改进；从逻辑上讲，存储位置仍然需要传递给方法，即使该存储位置的值没有被复制。由于 JIT 编译和优化的黑盒，我不会在这里做太多断言。在没有测试的情况下推理性能是一个坏主意：涉及的因素足够复杂，以至于这种推理最多只能成为有根据的猜测。然而，我预计随着涉及的结构体大小的增加，in 参数的好处也会增加。

          我对 in 参数的主要担忧是，它们会使你代码的推理变得困难。正如你在 13.3.2 节中看到的，你可以读取同一参数的值两次并得到不同的结果，尽管你的方法没有更改任何东西。这使得编写正确的代码变得困难，并且容易编写看起来正确但实际上不正确的代码。

          不过，有一种方法可以避免这种情况，同时仍然获得 in 参数的许多好处：通过仔细减少或消除它们更改的可能性。如果你有一个通过深层私有方法调用栈实现的公共 API，你可以为该公共 API 使用值参数，然后在私有方法中使用 in 参数。下面的清单提供了一个示例，尽管它没有进行任何有意义的计算。

          清单 13.14 安全地使用 in 参数

          public static double PublicMethod(
    LargeStruct first,
    LargeStruct second) //公共方法使用值参数
{
    double firstResult = PrivateMethod(in first);
    double secondResult = PrivateMethod(in second);
    return firstResult + secondResult;
}
private static double PrivateMethod(  //私有方法使用 in 参数
    in LargeStruct input)
{
    double scale = GetScale(in input);
    return (input.X + input.Y + input.Z) * scale;
}
private static double GetScale(in LargeStruct input) =>  //另一个使用 in 参数的方法
    input.Weight * input.Score;

          通过这种方法，你可以防止意外更改；因为所有方法都是私有的，你可以检查所有调用者以确保它们不会传递在方法执行期间可能更改的值。当调用 PublicMethod 时，每个结构体会被复制一次，但这些副本随后被别名用于私有方法中，从而使你的代码与调用者可能在其他线程中或作为其他方法的副作用进行的任何更改隔离开来。在某些情况下，你可能希望参数是可更改的，但要以你仔细记录和控制的方式。

          将相同的逻辑应用于内部调用也是合理的，但需要更多的纪律，因为有更多的代码可以调用该方法。就个人偏好而言，我明确在调用站点和参数声明中使用 in 修饰符，以使在阅读代码时清楚地知道发生了什么。

          我将所有这些总结为简短的建议列表：

          • 仅当存在可测量且显著的性能优势时才使用 in 参数。这最可能出现在涉及大型结构体时。
          • 避免在公共 API 中使用 in 参数，除非你的方法即使在方法执行期间参数值任意更改的情况下也能正确运行。
          • 考虑使用公共方法作为防止更改的屏障，然后在私有实现中使用 in 参数以避免复制。
          • 考虑在调用带有 in 参数的方法时明确使用 in 修饰符，除非你故意使用编译器通过引用传递隐藏局部变量的能力。

          这些指南中的许多都可以通过 Roslyn 分析器轻松检查。尽管在撰写本文时我不知道有这样的分析器，但我不会惊讶看到有 NuGet 包可用。

          注意 如果你在这里察觉到隐含的挑战，你是对的。如果你知道有这样的分析器，请告诉我，我会在网站上添加注释。

          所有这些都取决于真正减少了复制量，而这并不像听起来那么简单。我之前提到过这一点，但现在需要更仔细地查看编译器何时隐式复制结构体以及如何避免这种情况。

          将结构体声明为只读（C# 7.2）#

          in 参数的要点是通过减少结构体的复制来提高性能。这听起来很棒，但除非我们小心，否则 C# 的一个晦涩方面会妨碍我们。我们将首先查看问题，然后查看 C# 7.2 如何解决它。

          背景：使用只读变量隐式复制#

          C# 长期以来一直在隐式复制结构体。这都在规范中有记录，但直到我在 Noda Time 中偶然发现忘记使字段只读时获得了神秘的性能提升，我才意识到这一点。

          让我们看一个简单的例子。你将声明一个具有三个只读属性的 YearMonthDay 结构体：Year、Month 和 Day。你没有使用内置的 DateTime 类型，原因稍后会清楚。下面的清单显示了 YearMonthDay 的代码；它非常简单。（没有验证；仅用于本节的演示。）

          清单 13.15 一个简单的年/月/日结构体

          public struct YearMonthDay
{
    public int Year { get; }
    public int Month { get; }
    public int Day { get; }
    public YearMonthDay(int year, int month, int day) =>
        (Year, Month, Day) = (year, month, day);
}

          现在创建一个具有两个 YearMonthDay 字段的类：一个只读字段和一个读写字段。然后你将在两个字段中访问 Year 属性。

          清单 13.16 通过只读或读写字段访问属性

          class ImplicitFieldCopy
{
    private readonly YearMonthDay readOnlyField =
        new YearMonthDay(2018, 3, 1);
    private YearMonthDay readWriteField =
        new YearMonthDay(2018, 3, 1);
    public void CheckYear()
    {
        int readOnlyFieldYear = readOnlyField.Year;
        int readWriteFieldYear = readWriteField.Year;
    }
}

          为两个属性访问生成的 IL 在一个微妙但重要的方面有所不同。这是只读字段的 IL；为了简单起见，我从 IL 中移除了命名空间：

          ldfld valuetype YearMonthDay ImplicitFieldCopy::readOnlyField
stloc.0
ldloca.s V_0
call instance int32 YearMonthDay::get_Year()

          它加载字段的值，从而将其复制到堆栈上。只有这样它才能调用 get_Year() 成员，这是 Year 属性的 getter。将其与使用读写字段的代码进行比较：

          ldflda valuetype YearMonthDay ImplicitFieldCopy::readWriteField
call instance int32 YearMonthDay::get_Year()

          这使用 ldflda 指令将字段的地址加载到堆栈上，而不是 ldfld（它加载字段的值）。这只是 IL，不是计算机直接执行的。在某些情况下，JIT 编译器可能能够优化掉这一点，但在 Noda Time 中，我发现使字段读写（仅用一个属性解释它们为什么不是只读的）对性能有显著影响。

          编译器进行此复制是为了避免只读字段被属性（或方法，如果你正在调用一个方法）内的代码更改。只读字段的意图是没有任何东西可以更改其值。如果 readOnlyField.SomeMethod() 能够修改字段，那将很奇怪。C# 被设计为期望任何属性设置器都会改变数据，因此它们对只读字段完全禁止。但即使是属性 getter 也可能尝试改变值。复制是一种安全措施。

          这仅影响值类型 提醒一下，拥有一个引用类型的只读字段是可以的，并且方法可以改变它们引用的对象中的数据。例如，你可以有一个只读的 StringBuilder 字段，并且仍然可以追加到该 StringBuilder。字段的值只是引用，而这是无法更改的。

          在本节中，我们关注的是字段类型为值类型（如 decimal 或 DateTime）的情况。包含字段的类型是类还是结构体并不重要。

          在 C# 7.2 之前，只有字段可以是只读的。现在我们还有 ref readonly 局部变量和 in 参数需要担心。让我们写一个方法，从值参数打印年、月、日：

          private void PrintYearMonthDay(YearMonthDay input) =>
    Console.WriteLine($"{input.Year} {input.Month} {input.Day}");

          此方法的 IL 使用已经在堆栈上的值的地址。每个属性访问看起来都像这样简单：

          ldarga.s input
call instance int32 Chapter13.YearMonthDay::get_Year()

          这不会创建任何额外的副本。假设是，如果属性改变了值，更改你的 input 变量是可以的；毕竟，它只是一个读写变量。但如果你决定将 input 更改为 in 参数，如下所示，事情就变了：

          private void PrintYearMonthDay(in YearMonthDay input) =>
    Console.WriteLine($"{input.Year} {input.Month} {input.Day}");

          现在在方法的 IL 中，每个属性访问都有这样的代码：

          ldarg.1
ldobj Chapter13.YearMonthDay
stloc.0
ldloca.s V_0
call instance int32 YearMonthDay::get_Year()

          ldobj 指令从地址（参数）复制值到堆栈上。你试图避免调用者进行的一次复制，但这样做却在方法内引入了三次复制。使用 readonly ref 局部变量也会看到完全相同的行为。这不好！正如你可能猜到的，C# 7.2 有一个解决方案：只读结构体来拯救！

          结构体的 readonly 修饰符#

          回顾一下，C# 编译器需要为只读值类型变量进行复制的原因是为了避免这些类型内的代码更改变量的值。如果结构体可以承诺它不会这样做呢？毕竟，大多数结构体被设计为不可变的。在 C# 7.2 中，你可以将 readonly 修饰符应用于结构体声明来做到这一点。

          让我们修改我们的年/月/日结构体为只读。它已经在实现中遵守了语义，所以你只需要添加 readonly 修饰符：

          public readonly struct YearMonthDay
{
    public int Year { get; }
    public int Month { get; }
    public int Day { get; }
    public YearMonthDay(int year, int month, int day) =>
        (Year, Month, Day) = (year, month, day);
}

          在简单更改声明后，并且在使用结构体的代码没有任何更改的情况下，为 PrintYearMonthDay(in YearMonthDay input) 生成的 IL 变得更高效。现在每个属性访问看起来像这样：

          ldarg.1
call instance int32 YearMonthDay::get_Year()

          最后，你设法避免了整个结构体的复制，甚至一次都没有。

          如果你查看本书附带的可下载源代码，你会看到这在单独的结构体声明中：ReadOnlyYearMonthDay。这是必要的，这样我就可以有前后示例，但在你自己的代码中，你可以使现有结构体变为只读，而不会破坏源或二进制兼容性。然而，相反方向则是一个阴险的破坏性更改；如果你决定删除修饰符并修改现有成员以改变值的状态，那么先前编译的期望结构体为只读的代码可能会以令人震惊的方式改变只读变量。

          只有当你的结构体是真正的只读并且因此满足以下条件时，你才能应用该修饰符：

          • 每个实例字段和自动实现的实例属性必须是只读的。静态字段和属性仍然可以是读写的。
          • 你只能在构造函数内赋值给 this。用规范术语来说，在构造函数中 this 被视为 out 参数，在常规结构体的成员中视为 ref 参数，在只读结构体的成员中视为 in 参数。

          假设你本来就想让你的结构体是只读的，添加 readonly 修饰符允许编译器通过检查你没有违反这一点来帮助你。我期望大多数用户定义的结构体都能立即工作。不幸的是，当涉及到 Noda Time 时，有一个小问题，这可能也会影响你。

          XML 序列化是隐式读写的#

          目前，Noda Time 中的大多数结构体实现了 IXmlSerializable。不幸的是，XML 序列化的定义方式对编写只读结构体充满敌意。我在 Noda Time 中的实现通常如下所示：

          void IXmlSerializable.ReadXml(XmlReader reader)
{
    var pattern = /* 某种适合该类型的文本解析模式 */;
    var text = /* 从 XmlReader 中提取文本 */;
    this = pattern.Parse(text).Value;
}

          你能看出问题吗？它在最后一行赋值给了 this。这阻止了我用 readonly 修饰符声明这些结构体，这让我很伤心。目前我有三个选择：

          • 保持结构体原样，这意味着 in 参数和 ref readonly 局部变量是低效的。
          • 从 Noda Time 的下一个主要版本中移除 XML 序列化。
          • 在 ReadXml 中使用不安全代码来违反 readonly 修饰符。System.Runtime.CompilerServices.Unsafe 包使这变得更简单。

          这些选项都不令人愉快，而且当我揭示一个狡猾的方法来满足所有关注点时，并没有转折。目前，我相信实现 IXmlSerializable 的结构体不能是真正的只读。毫无疑问，还有其他接口在结构体中实现时是隐式可变的，但我怀疑 IXmlSerializable 将是最常见的。

          好消息是，大多数读者可能没有面临这个问题。在可以的情况下，我鼓励你使你定义的结构体变为只读。只是请记住，对于公共代码来说，这是一个单向更改；只有在能够重新编译所有使用该结构体的代码的特权位置时，你才能安全地在以后移除修饰符。我们的下一个特性实际上是整理一致性：为扩展方法提供与结构体实例方法已有的相同功能。

          本节深入探讨了 C# 7.2 引入的 in 参数和只读结构体。in 参数旨在通过引用传递大型结构体以避免复制，从而提升性能，但它引入了潜在风险：作为存储位置别名的 in 参数可能被其他代码（如委托回调或多线程）意外修改，破坏了方法内部的不可变性假设。这要求开发者谨慎设计，建议仅在性能关键路径且能控制所有调用时使用，或在私有方法中使用以隔离风险。

          只读结构体（readonly struct）则解决了与 in 参数和 ref readonly 配合时隐式复制的问题。当结构体声明为 readonly 时，编译器能确保其不可变性，从而安全地通过引用传递而无需防御性复制。但需注意，某些框架接口（如 IXmlSerializable）因设计限制（需赋值给 this）与只读结构体不兼容，可能导致取舍。

          总体而言，这些特性为高性能场景提供了精细控制，但应基于实际性能度量使用，并优先考虑代码安全性与可维护性。它们与 Span<T> 等特性共同推动 C# 向系统级编程领域深化。

          带ref或in参数的扩展方法（C# 7.2）#

          在C# 7.2之前，任何扩展方法的第一个参数必须是值参数。这个限制在C# 7.2中部分解除，以更全面地接纳新的引用语义。

          在扩展方法中使用ref/in参数避免复制#

          假设你有一个大型结构体希望避免复制，并且有一个基于该结构体属性值计算结果的方法——例如，三维向量的模长。如果结构体本身提供了这个方法（或属性），那就没问题，特别是如果结构体是用readonly修饰符声明的。你可以毫无问题地避免复制。但也许你在做一些结构体作者没有考虑的更复杂的事情。

          如果你编写自己的方法，接受一个带有in参数的结构体，你可以避免复制，但调用起来可能有点笨拙。使用扩展方法会更优雅，但常规扩展方法会在每次调用时复制结构体。C# 7.2允许你编写第一个参数带有ref或in修饰符的扩展方法，从而在性能和可读性之间取得平衡。

          ref和in扩展方法的限制#

          正常扩展方法可以扩展任何类型，而ref和in扩展方法必须扩展值类型。对于in扩展方法，该值类型也不能是类型参数。ref扩展方法的类型参数必须有struct约束。

          主要原因有两个：

          1. 该特性旨在避免值类型的昂贵复制，对于引用类型没有好处
          2. 如果ref参数可以是引用类型，则可能在方法内将其设置为null，这会破坏C#开发人员和工具的现有假设

          类似引用的结构体（C# 7.2）#

          C# 7.2引入了类似引用的结构体概念：一种只存在于栈上的结构体。其核心原则是：类似引用的结构体值必须始终留在栈上。

          类似引用结构体的规则#

          类似引用的结构体有许多限制以确保它们始终在栈上：

          • 不能作为非类似引用结构体类型的字段
          • 不能装箱
          • 不能用作泛型类型参数
          • 不能在异步方法、迭代器块中跨await或yield使用
          • 不能被lambda表达式或匿名方法捕获

          Span<T>和stackalloc#

          Span<T>是一个类似引用的结构体，它提供对内存块的读写、索引访问，就像数组一样，但没有任何拥有该内存的概念。其主要优势包括：

          1. 可以引用具有严格受控生命周期的内存，因为span不能从栈中逃逸
          2. 允许在span中自定义一次性初始化数据，无需复制

          Span<T>使得编写高性能代码变得更加安全，因为它可以确保内存安全，同时避免了不必要的复制。string.Create方法结合Span<T>可以实现零复制字符串创建，这是性能优化的重要工具。

          类似引用结构体的IL表示#

          类似引用的结构体用[IsRefLikeAttribute]属性修饰。与in参数不同，编译器不使用modreq修饰符，而是添加一个带有特定消息的[ObsoleteAttribute]，以便理解[IsRefLikeAttribute]的编译器可以忽略它。

          C# 7在语言的许多领域增加了对按引用语义的支持：

          • C# 7.0引入了引用局部变量和引用返回
          • C# 7.2引入了in参数、只读引用、只读结构体和类似引用结构体
          • C# 7.3进一步增强了这些特性

          与引用相关的主要特性是为了性能优化。如果你不是在编写性能关键的代码，可能不需要直接使用这些特性。但通过框架提供的抽象（如Span<T>），大多数开发者将间接受益于这些特性带来的性能提升。

          类似引用的结构体允许在框架中引入新的抽象，从Span<T>开始。这些抽象不仅适用于高性能场景；随着时间的推移，它们可能会影响大部分.NET开发人员，使编写高性能、内存安全的代码变得更加容易。
