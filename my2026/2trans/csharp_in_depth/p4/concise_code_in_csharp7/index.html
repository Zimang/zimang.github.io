          C# 7带来了一些大型特性，这些特性改变了我们编写代码的方式：元组、解构和模式匹配。它还带来了一些复杂但高效的特性，这些特性直接针对高性能场景。此外，它还包含一组小特性，这些特性只是让生活变得更美好一些。本章中没有哪个特性是惊天动地的；每个特性都只带来一点小改变，但将它们组合起来可以带来非常简洁、清晰的代码。

          局部方法#

          如果不是《C#深入解析》这本书，这一节可能会很短；你可以在方法内部编写方法。当然，这还不止，但让我们从一个简单的例子开始。下面的清单展示了一个常规Main方法中的一个简单局部方法。局部方法打印并递增Main中声明的局部变量，演示了变量捕获在局部方法中的工作原理。

          清单14.1 访问局部变量的简单局部方法

          static void Main()
{
    int x = 10;
    PrintAndIncrementX();
    PrintAndIncrementX();
    Console.WriteLine($"After calls, x = {x}");
    
    void PrintAndIncrementX()
    {
        Console.WriteLine($"x = {x}");
        x++;
    }
}

          当你第一次看到这个时，可能会觉得有点奇怪，但你很快就会习惯。局部方法可以出现在任何有语句块的地方：方法、构造函数、属性、索引器、事件访问器、终结器，甚至可以在匿名函数内部或另一个局部方法内部嵌套。

          局部方法声明类似于普通方法声明，但有以下限制：

          • 不能有任何访问修饰符（public等）
          • 不能有extern、virtual、new、override、static或abstract修饰符
          • 不能有任何特性（例如[MethodImpl]）应用于它
          • 不能与同一父级中的另一个局部方法同名；无法重载局部方法

          另一方面，局部方法在其他方面类似于标准方法，例如：

          • 可以是void或返回值
          • 可以有async修饰符
          • 可以有unsafe修饰符
          • 可以通过迭代器块实现
          • 可以有参数，包括可选参数
          • 可以是泛型的
          • 可以引用任何封闭类型参数
          • 可以是方法组转换到委托类型的目标

          如清单14.1所示，在方法使用之后声明方法是完全可行的。局部方法可以调用自身或作用域内的其他局部方法。然而，位置仍然很重要，主要是在局部方法如何引用捕获的变量方面：在封闭代码中声明但在局部方法中使用的局部变量。

          实际上，局部方法的大部分复杂性，无论是语言规则还是实现，都围绕它们读写捕获变量的能力。让我们从语言施加的规则开始讨论。

          局部方法中的变量访问#

          你已经看到，封闭块中的局部变量可以被读取和写入，但还有更多的细微差别。这里有很多小规则，但你不需要担心详尽地学习它们。大多数时候你甚至不会注意到它们，如果编译器抱怨你期望有效的代码，你可以参考本节。

          局部方法只能捕获作用域内的变量 你不能引用作用域之外的局部变量，一般来说，就是声明它的块。例如，假设你希望局部方法使用在循环中声明的迭代变量；局部方法本身也必须声明在循环中。作为一个简单的例子，这是无效的：

          static void Invalid()
{
    for (int i = 0; i < 10; i++)
    {
        PrintI();
    }
    void PrintI() => Console.WriteLine(i);  // 无法访问i；它不在作用域内
}

          但是将局部方法放在循环内部，就是有效的：

          static void Valid()
{
    for (int i = 0; i < 10; i++)
    {
        void PrintI() => Console.WriteLine(i);  // 局部方法声明在循环内；i在作用域内
        PrintI();
    }
}

          局部方法必须在任何它捕获的变量声明之后声明 就像在常规代码中不能早于变量的声明使用变量一样，你也不能在局部方法中使用捕获变量直到其声明之后。这个规则更多是为了一致性而不是必要性；例如，本来可以指定语言要求任何对方法的调用都发生在变量声明之后，但要求所有访问都发生在声明之后更简单。这是另一个无效代码的简单例子：

          static void Invalid()
{
    void PrintI() => Console.WriteLine(i);  // CS0841: 不能在局部变量i声明前使用它
    int i = 10;
    PrintI();
}

          只需将局部方法声明移动到变量声明之后（无论是在PrintI()调用之前还是之后）即可修复错误。

          局部方法不能捕获封闭方法的ref参数 就像匿名函数一样，局部方法不允许使用其封闭方法的引用参数。例如，这是无效的：

          static void Invalid(ref int p)
{
    void PrintAndIncrementP() => Console.WriteLine(p++);  // 对引用参数的无效访问
    PrintAndIncrementP();
}

          对于匿名函数来说，这个禁令的原因在于创建的委托可能比被捕获的变量存活得更久。在大多数情况下，这个原因不适用于局部方法，但正如你稍后将看到的，局部方法可能有同样的问题。在大多数情况下，你可以通过在局部方法中声明一个额外的参数并再次通过引用传递引用参数来解决这个问题：

          static void Valid(ref int p)
{
    void PrintAndIncrement(ref int x) => Console.WriteLine(x++);
    PrintAndIncrement(ref p);
}

          如果你不需要在局部方法中修改参数，你可以将其改为值参数。

          作为这个限制的推论（再次，反映了匿名函数的限制），在结构体内声明的局部方法不能访问this。想象一下，这是每个实例方法参数列表开头的一个隐式额外参数。对于类方法，它是一个值参数；对于结构体方法，它是一个引用参数。因此，你可以在类的局部方法中捕获this，但不能在结构体中。与其他引用参数相同的解决方法也适用。

          注意：我在本书附带的源代码中的LocalMethodUsingThisInStruct.cs中提供了一个例子。

          局部方法与明确赋值交互 C#中的明确赋值规则很复杂，而局部方法使它们更加复杂。最简单的方法是将方法视为在调用它的任何地方内联。这以两种方式影响赋值。

          首先，如果在一个捕获变量被明确赋值之前调用了读取该变量的方法，那会导致编译时错误。这是一个尝试在两个地方打印捕获变量值的例子：一次是在它被赋值之前，一次是在之后：

          static void AttemptToReadNotDefinitelyAssignedVariable()
{
    int i;
    void PrintI() => Console.WriteLine(i);
    PrintI();  // CS0165: 使用了未赋值的局部变量'i'
    i = 10;
    PrintI();  // 没有错误：i在这里已明确赋值
}

          注意，这里导致错误的是调用PrintI的位置；方法声明本身的位置是没问题的。如果你将i的赋值移到任何调用PrintI()之前，那是没问题的，即使它仍然在PrintI()声明之后。

          其次，如果局部方法在所有可能的执行流程中都写入一个捕获变量，那么在任何调用该方法结束时，该变量将被明确赋值。这是一个在局部方法中赋值但然后在包含方法中读取的例子：

          static void DefinitelyAssignInMethod()
{
    int i;
    void AssignI() => i = 10;  // 方法执行赋值
    AssignI();  // 对该方法的调用使i明确赋值
    Console.WriteLine(i);  // 所以打印它是没问题的
}

          关于局部方法和变量还有最后几点要说明，但这次讨论的变量不是捕获变量，而是字段。

          局部方法不能赋值给只读字段 只读字段只能在字段初始化器或构造函数中赋值。这个规则不因局部方法而改变，但变得更严格一些：即使局部方法在构造函数中声明，在字段初始化方面也不算在构造函数内部。这段代码无效：

          class Demo
{
    private readonly int value;
    public Demo()
    {
        void AssignValue()
        {
            value = 10;  // 对只读字段的无效赋值
        }
        AssignValue();
    }
}

          这个限制可能不是一个重要的问题，但值得注意。它源于CLR不必为了支持局部方法而改变的事实。它们只是一种编译器转换。这引导我们思考编译器如何实现局部方法，特别是关于捕获变量。

          局部方法的实现#

          局部方法在CLR级别不存在。C#编译器通过执行所需的任何转换将局部方法转换为常规方法，以使最终代码按照语言规则行为。本节提供了Roslyn（微软C#编译器）实现的转换示例，并重点关注捕获变量如何处理，因为这是转换中最复杂的方面。

          实现细节：这里没有任何保证 本节确实是关于C# 7.0版本的Roslyn如何实现局部方法。这个实现在未来版本的Roslyn中可能会改变，其他C#编译器可能使用不同的实现。这也意味着这里有很多你可能不感兴趣的细节。

          该实现确实具有性能影响，可能会影响你在性能敏感代码中使用局部方法的舒适度。但像所有性能问题一样，你应该更多地基于仔细的测量而不是理论来做出决定。

          局部方法在捕获周围代码中的局部变量方面感觉像匿名函数。但实现上的显著差异可以使局部方法在许多情况下更高效。这种差异的根源在于所涉及的局部变量的生命周期。如果匿名函数被转换为委托实例，该委托可能在方法返回后很久才被调用，因此编译器必须执行技巧，将捕获变量提升到一个类中，并使委托引用该类中的一个方法。

          与局部方法相比：在大多数情况下，局部方法只能在封闭方法的调用期间被调用；你不需要担心它在那次调用完成后引用捕获变量。这允许一种更高效的、基于栈的实现，没有堆分配。让我们从一个简单的局部方法开始，该方法按指定数量递增一个捕获变量。

          清单14.2 修改局部变量的局部方法

          static void Main()
{
    int i = 0;
    void AddToI(int amount) => i += amount;
    AddToI(5);
    AddToI(10);
    Console.WriteLine(i);
}

          Roslyn如何处理这个方法？它创建一个私有的可变结构体，其中包含公共字段，以表示同一作用域中被任何局部方法捕获的所有局部变量。在这种情况下，只有变量i。它在Main方法中创建该结构体类型的局部变量，并通过引用将该变量传递给从AddToI生成的常规方法，当然还有声明的数量参数。你最终得到类似以下清单的内容。

          清单14.3 Roslyn对清单14.2的处理

          private struct MainLocals  // 生成的可变结构体，用于存储Main中的局部变量
{
    public int i;
}

static void Main()
{
    MainLocals locals = new MainLocals();  // 在方法中创建并使用结构体的值
    locals.i = 0;
    AddToI(5, ref locals);  // 通过引用将结构体传递给生成的方法
    AddToI(10, ref locals);
    Console.WriteLine(locals.i);
}

static void AddToI(int amount, ref MainLocals locals)  // 生成的方法，表示原始局部方法
{
    locals.i += amount;
}

          像往常一样，编译器为方法和结构体生成不可说的名称。注意，在这个例子中，生成的方法是静态的。当局部方法最初包含在静态成员中，或者当它包含在实例成员中但局部方法没有捕获this（通过使用局部方法中的实例成员显式或隐式）时，就是这种情况。

          关于生成这个结构体的重要点是，这种转换在性能方面几乎是免费的：所有之前会在栈上的局部变量仍然在栈上；它们只是在一个结构体中捆绑在一起，以便可以通过引用传递给生成的方法。通过引用传递结构体有两个好处：

          • 它允许局部方法修改局部变量。
          • 无论捕获多少局部变量，调用局部方法都是廉价的。（与按值传递它们相比，这将意味着为每个捕获的局部变量创建第二个副本。）

          所有这些都没有在堆上生成任何垃圾。万岁！现在让我们让事情变得更复杂一些。

          在多个作用域中捕获变量 在匿名函数中，如果从多个作用域捕获局部变量，则会生成多个类，每个类中有一个字段，内层作用域的类持有外层作用域类实例的引用。这对于你刚才看到的局部方法的结构体方法不起作用，因为涉及复制。相反，编译器为每个包含捕获变量的作用域生成一个结构体，并为每个作用域使用一个单独的参数。清单14.4故意创建了两个作用域，以便我们可以看到编译器如何处理它。

          清单14.4 从多个作用域捕获变量

          static void Main()
{
    DateTime now = DateTime.UtcNow;
    int hour = now.Hour;
    if (hour > 5)
    {
        int minute = now.Minute;
        void PrintValues() => Console.WriteLine($"hour = {hour}; minute = {minute}");
        PrintValues();
    }
}

          我使用了一个简单的if语句来引入一个新的作用域，而不是for或foreach循环，因为这使得转换更简单，可以合理地准确表示。下面的清单展示了编译器如何将局部方法转换为常规方法。

          清单14.5 Roslyn对清单14.4的处理

          struct OuterScope  // 为外层作用域生成的结构体
{
    public int hour;
}

struct InnerScope  // 为内层作用域生成的结构体
{
    public int minute;
}

static void Main()
{
    DateTime now = DateTime.UtcNow;  // 未捕获的局部变量
    OuterScope outer = new OuterScope();  // 为外层作用域变量hour创建并使用结构体
    outer.hour = now.Hour;
    if (outer.hour > 5)
    {
        InnerScope inner = new InnerScope();  // 为内层作用域变量minute创建并使用结构体
        inner.minute = now.Minute;
        PrintValues(ref outer, ref inner);  // 通过引用将两个结构体传递给生成的方法
    }
}

static void PrintValues(ref OuterScope outer, ref InnerScope inner)  // 生成的方法，表示原始局部方法
{
    Console.WriteLine($"hour = {outer.hour}; minute = {inner.minute}");
}

          除了展示如何处理多个作用域外，这个清单还显示未捕获的局部变量不包含在生成的结构体中。

          到目前为止，我们已经看了局部方法只能在包含方法执行期间执行的情况，这使得以这种高效方式捕获局部变量是安全的。根据我的经验，这涵盖了我想要使用局部方法的大多数情况。不过，偶尔也有例外情况。

          越狱！局部方法如何逃逸其包含代码 局部方法在四种情况下表现得像常规方法，这会阻止编译器执行我们迄今为止讨论的"将所有内容保留在栈上"优化：

          • 它们可以是异步的，因此返回任务几乎立即的调用不一定已经完成了逻辑操作。
          • 它们可以用迭代器实现，因此创建序列的调用需要在请求序列中的下一个值时继续执行方法。
          • 它们可以从匿名函数中调用，而这些匿名函数又可能在原始方法完成后很久才被调用（作为委托）。
          • 它们可以是方法组转换的目标，再次创建可以比原始方法调用寿命更长的委托。

          下面的清单展示了最后一个要点的简单例子。一个局部Count方法捕获其封闭CreateCounter方法中的一个局部变量。Count方法用于创建一个Action委托，然后在CreateCounter方法返回后调用该委托。

          清单14.6 局部方法的方法组转换

          static void Main()
{
    Action counter = CreateCounter();
    counter();  // 在CreateCounter完成后调用委托
    counter();
}

static Action CreateCounter()
{
    int count = 0;  // 被Count捕获的局部变量
    void Count() => Console.WriteLine(count++);  // 局部方法
    return Count;  // Count的方法组转换为Action委托
}

          你现在不能再在栈上使用结构体来表示count了。CreateCounter的栈在委托被调用时已经不存在了。但这现在感觉非常像一个匿名函数；你可以使用lambda表达式来实现CreateCounter：

          static Action CreateCounter()
{
    int count = 0;
    return () => Console.WriteLine(count++);  // 使用lambda表达式的替代实现
}

          这给你一个提示，编译器如何实现局部方法：它可以对局部方法应用与lambda表达式类似的转换，如清单14.7所示。

          清单14.7 Roslyn对清单14.6的处理

          static void Main()
{
    Action counter = CreateCounter();
    counter();
    counter();
}

static Action CreateCounter()
{
    CountHolder holder = new CountHolder();  // 创建并初始化持有捕获变量的对象
    holder.count = 0;
    return holder.Count;  // holder实例方法的方法组转换
}

private class CountHolder  // 带有捕获变量和局部方法的私有类
{
    public int count;  // 捕获的变量
    public void Count() => Console.WriteLine(count++);  // 局部方法现在是生成类中的实例方法
}

          如果局部方法在匿名函数中使用，或者它是异步方法，或者是迭代器（带有yield语句），则会执行相同类型的转换。注重性能的人可能希望注意，异步方法和迭代器可能最终生成多个对象；如果你正在努力防止分配并且正在使用局部方法，你可能希望显式地将参数传递给这些局部方法，而不是捕获局部变量。下一节将展示一个例子。

          当然，可能的场景非常多；一个局部方法可以用于另一个局部方法的方法转换，或者你可以在异步方法中使用局部方法，等等。我肯定不会在这里尝试覆盖所有可能的情况。本节旨在让你了解编译器在处理捕获变量时可以使用的两种转换。要查看编译器对你的代码做了什么，请使用反编译器或ildasm，记住禁用反编译器可能为你做的任何"优化"。（否则，它可能很容易只显示局部方法，这对你完全没有帮助。）现在你已经看到了局部方法可以做什么以及编译器如何处理它们，让我们考虑何时适合使用它们。

          使用指南#

          有两种主要模式可以识别局部方法可能适用的情况：

          • 你在一个方法中多次重复相同的逻辑。
          • 你有一个只被另一个方法使用的私有方法。

          第二种情况是第一种情况的特例，即你已经花时间重构了公共代码。但第一种情况可能发生在有足够多的局部状态使得重构变得丑陋时。局部方法可以使提取变得更有吸引力，因为能够捕获局部变量。

          当将现有方法重构为局部方法时，我建议有意识地采取两阶段方法。首先，将单次使用的方法移动到使用它的代码中，而不改变其签名。其次，查看方法参数：对该方法的所有调用是否都使用相同的局部变量作为参数？如果是，那么这些是使用捕获变量的好候选，从局部方法中移除参数。有时你甚至可能能够完全移除参数。

          根据参数的数量和大小，第二步甚至可能对性能产生影响。如果你之前是按值传递大型值类型，那么每次调用都会复制它们。使用捕获变量可以消除这种复制，如果方法被调用很多次，这可能很重要。

          关于局部方法的重要一点是，很明显它们是方法的实现细节，而不是类型的实现细节。如果你有一个私有方法，它本身作为一个操作是有意义的，但碰巧目前只在一个地方使用，你可能最好保持原样。当一个私有方法与单个操作紧密绑定，并且你无法轻易想象任何其他使用情况时，回报（在逻辑类型结构方面）会大得多。

          迭代器/异步参数验证和局部方法优化 一个常见的例子是，当你有迭代器或异步方法并希望尽早执行参数验证时。例如，清单14.8提供了LINQ to Objects中Select的一个重载的示例实现。参数验证不在迭代器块中，因此一旦调用方法就会执行，而foreach循环在调用者开始迭代返回的序列之前根本不会执行。

          清单14.8 没有局部方法的Select实现

          public static IEnumerable<TResult> Select<TSource, TResult>(
    this IEnumerable<TSource> source,
    Func<TSource, TResult> selector)
{
    Preconditions.CheckNotNull(source, nameof(source));  // 尽早检查参数
    Preconditions.CheckNotNull(selector, nameof(selector));
    return SelectImpl(source, selector);  // 委托给实现
}

private static IEnumerable<TResult> SelectImpl<TSource, TResult>(
    IEnumerable<TSource> source,
    Func<TSource, TResult> selector)
{
    foreach (TSource item in source)  // 实现延迟执行
    {
        yield return selector(item);
    }
}

          现在，有了局部方法，你可以将实现移动到Select方法中，如清单14.9所示。

          清单14.9 使用局部方法实现Select

          public static IEnumerable<TResult> Select<TSource, TResult>(
    this IEnumerable<TSource> source,
    Func<TSource, TResult> selector)
{
    Preconditions.CheckNotNull(source, nameof(source));
    Preconditions.CheckNotNull(selector, nameof(selector));
    return SelectImpl(source, selector);
    
    IEnumerable<TResult> SelectImpl(
        IEnumerable<TSource> validatedSource,
        Func<TSource, TResult> validatedSelector)
    {
        foreach (TSource item in validatedSource)
        {
            yield return validatedSelector(item);
        }
    }
}

          我强调了实现的一个有趣方面：你仍然将（现在已验证的）参数传递给局部方法。这不是必须的；你可以使局部方法无参数，只使用捕获的source和selector变量，但这是一个性能调整——它减少了所需的分配数量。这种性能差异重要吗？使用变量捕获的版本是否明显更可读？这两个问题的答案都取决于上下文，可能有些主观。

          可读性建议 局部方法对我来说仍然足够新，以至于我对它们有些谨慎。我目前倾向于保持代码原样，而不是重构为局部方法。特别是，我避免使用以下两个特性：

          • 尽管你可以在循环或其他块的作用域内声明局部方法，但我觉得读起来很奇怪。我更喜欢只在可以在封闭方法的底部声明局部方法时使用它们。我不能捕获循环内声明的变量，但我可以接受。
          • 你可以在其他局部方法中声明局部方法，但这感觉像是一个我不想进入的兔子洞。

          当然，你的口味可能不同，但像往常一样，我警告不要仅仅因为你可以就使用新特性。（当然，为了实验而实验，但不要让新的闪亮的东西引诱你牺牲可读性。）

          现在是好消息的时候了：本章的第一个特性是大的。剩下的特性要简单得多。

          局部方法是C# 7中一项看似简单但实际强大的特性。它允许在方法内部定义辅助方法，显著提高了代码的封装性和可读性。局部方法的核心价值在于它能够自然地捕获所在作用域的变量，避免了将局部变量作为参数传递的繁琐，同时保持了逻辑的内聚性。

          从实现角度看，编译器会智能地处理局部方法：在大多数情况下，它通过生成栈上的结构体来避免堆分配，确保高性能；只有当局部方法可能逃逸当前作用域（如转换为委托、用于异步或迭代器）时，才采用类似匿名函数的类包装方式。

          使用局部方法的最佳场景包括：重复逻辑的提取、迭代器/异步方法的参数验证，以及替代仅被单一方法使用的私有辅助方法。虽然局部方法增强了代码的表达力，但仍需谨慎使用，避免过度嵌套和滥用，以保持代码的清晰性。它代表了C#向更函数式、更灵活编程风格的迈进。

          out变量#

          在C# 7之前，out参数使用起来有点痛苦。一个out参数要求在使用它作为参数之前已经声明了一个变量。因为声明是单独的语句，这意味着在某些你想要单个表达式的地方（例如初始化变量），你必须重新组织代码以使用多个语句。

          out参数的内联变量声明#

          C# 7通过在方法调用本身中允许声明新变量来消除这个痛点。作为一个简单的例子，考虑一个方法，它接受文本输入，尝试使用int.TryParse将其解析为整数，然后返回解析后的值作为可空整数（如果解析成功）或null（如果不成功）。在C# 6中，必须使用至少两个语句来实现：一个声明变量，第二个调用int.TryParse，将新声明的变量传递给out参数：

          static int? ParseInt32(string text)
{
    int value;
    return int.TryParse(text, out value) ? value : (int?) null;
}

          在C# 7中，value变量可以在方法调用本身中声明，这意味着你可以使用表达式体实现该方法：

          static int? ParseInt32(string text) =>
    int.TryParse(text, out int value) ? value : (int?) null;

          在多个方面，out变量参数的行为类似于模式匹配引入的变量：

          • 如果你不关心该值，你可以使用单个下划线作为名称来创建丢弃。
          • 你可以使用var声明一个隐式类型变量（类型从参数的类型推断）。
          • 你不能在表达式树中使用out变量参数。
          • 变量的作用域是周围的块。
          • 在C# 7.3之前，你不能在字段、属性或构造函数初始化器或查询表达式中使用out变量。你很快就会看到一个例子。
          • 变量将被明确赋值当且仅当方法被明确调用。

          为了演示最后一点，考虑以下代码，它尝试解析两个字符串并对结果求和：

          static int? ParseAndSum(string text1, string text2) =>
    int.TryParse(text1, out int value1) &&
    int.TryParse(text2, out int value2)
    ? value1 + value2 : (int?) null;

          在条件运算符的第三个操作数中，value1是明确赋值的（所以如果你愿意，可以返回它），但value2不是明确赋值的；如果第一次调用int.TryParse返回false，由于&&运算符的短路特性，你将不会第二次调用int.TryParse。

          C# 7.3中out变量和模式变量限制的解除#

          正如我在12.5节提到的，模式变量不能在初始化字段或属性、构造函数初始化器（this(...)和base(...)）或查询表达式中使用。同样的限制适用于out变量，直到C# 7.3解除了所有这些限制。清单14.10演示了这一点，并显示out变量的结果在构造函数体内也可用。

          清单14.10 在构造函数初始化器中使用out变量

          class ParsedText
{
    public string Text { get; }
    public bool Valid { get; }
    
    protected ParsedText(string text, bool valid)
    {
        Text = text;
        Valid = valid;
    }
}

class ParsedInt32 : ParsedText
{
    public int? Value { get; }
    
    public ParsedInt32(string text)
        : base(text, int.TryParse(text, out int parseResult))
    {
        Value = Valid ? parseResult : (int?) null;
    }
}

          尽管在C# 7.3之前的限制从未困扰过我，但现在它们被解除了，这很好。在罕见的情况下，你需要为初始化器使用模式或out变量，替代方案相对烦人，通常涉及为此目的创建一个新方法。

          关于out变量参数就这些。它们只是一个有用的小速记，以避免其他烦人的变量声明语句。

          数字字面量的改进#

          在C#的历史中，字面量变化不大。从C# 1到C# 6完全没有变化，当时引入了插值字符串字面量，但那根本没有改变数字。在C# 7中，有两个特性针对数字字面量，两者都是为了提高可读性：二进制整数字面量和下划线分隔符。

          二进制整数字面量#

          与浮点字面量（用于float、double和decimal）不同，整数字面量一直有两个基数选项：你可以使用十进制（无前缀）或十六进制（前缀为0x或0X）。C# 7将其扩展到二进制字面量，它使用前缀0b或0B。如果你正在实现一个协议，其中某些值有特定的位模式，这尤其有用。它根本不影响执行时行为，但它可以使代码更容易阅读。例如，以下哪一行初始化了一个字节，其中最高位和最低三位被设置，其他位未设置？

          byte b1 = 135;
byte b2 = 0x83;
byte b3 = 0b10000111;

          它们都做到了。但你可以很容易地在第三行看出，而其他两行需要稍长一点的时间来检查（至少对我来说）。即使最后一行也比可能的时间长，因为你仍然需要检查总共有正确的位数。要是有办法能更清楚地说明就好了。

          下划线分隔符#

          让我们通过改进前面的例子直接进入下划线分隔符。如果你想指定一个字节的所有位并用二进制表示，更容易看出你有两个半字节，而不是数所有八位。这是相同的代码，第四行使用下划线分隔半字节：

          byte b1 = 135;
byte b2 = 0x83;
byte b3 = 0b10000111;
byte b4 = 0b1000_0111;

          喜欢它！我真的可以一眼就检查出来。不过，下划线分隔符不仅限于二进制字面量，甚至不仅限于整数字面量。你可以在任何数字字面量中使用它们，并将它们放在字面量内的（几乎）任何地方。在十进制字面量中，你最可能每三位使用一次，就像千位分隔符（至少在西方的文化中）。在十六进制字面量中，它们通常每两位、四位或八位最有用，以分隔字面量内的8位、16位或32位部分。例如：

          int maxInt32 = 2_147_483_647;
decimal largeSalary = 123_456_789.12m;
ulong alternatingBytes = 0xff_00_ff_00_ff_00_ff_00;
ulong alternatingWords = 0xffff_0000_ffff_0000;
ulong alternatingDwords = 0xffffffff_00000000;

          这种灵活性是有代价的：编译器不检查你是否将下划线放在合理的位置。你甚至可以将多个下划线放在一起。有效但不幸的例子包括：

          int wideFifteen = 1____________________5;
ulong notQuiteAlternatingWords = 0xffff_000_ffff_0000;

          你还应该注意一些限制：

          • 你不能在字面量的开头放置下划线。
          • 你不能在字面量的结尾放置下划线（包括后缀之前）。
          • 你不能在浮点字面量中的小数点前后直接放置下划线。
          • 在C# 7.0和7.1中，你不能在整数字面量的基数说明符（0x或0b）后放置下划线。

          最后的限制在C# 7.2中已被解除。尽管可读性是主观的，但我肯定更喜欢在基数说明符后使用下划线，当其他地方有下划线时，如下例所示：

          • 0b_1000_0111 对比 0b1000_0111
          • 0x_ffff_0000 对比 0xffff_0000

          就这样！一个很好的简单特性，几乎没有什么细微差别。下一个特性类似地直接，并允许在某些需要条件性抛出异常的情况下简化。

          throw表达式#

          早期版本的C#总是包含throw语句，但你不能将throw用作表达式。推测其理由是，你不会想这样做，因为它总是会抛出异常。事实证明，随着更多需要表达式的语言特性被添加，这种分类变得越来越令人恼火。在C# 7中，你可以在有限的上下文中使用throw表达式：

          • 作为lambda表达式的主体
          • 作为表达式体成员的主体
          • 作为??运算符的第二个操作数
          • 作为条件?:运算符的第二个或第三个操作数（但不能在同一表达式中同时出现）

          所有这些都有效：

          public void UnimplementedMethod() =>
    throw new NotImplementedException();  // 表达式体方法

public void TestPredicateNeverCalledOnEmptySequence()
{
    int count = new string[0]
        .Count(x => throw new Exception("Bang!"));  // Lambda表达式
    Assert.AreEqual(0, count);
}

public static T CheckNotNull<T>(T value, string paramName) where T : class
    => value ?? throw new ArgumentNullException(paramName);  // ??运算符（在表达式体方法中）

public static Name =>
    initialized
    ? data["name"]
    : throw new Exception("...");  // ?:运算符（在表达式体属性中）

          不过，你不能在任何地方使用throw表达式；那将没有意义。例如，你不能在赋值中无条件使用它们或作为方法参数：

          int invalid = throw new Exception("This would make no sense");
Console.WriteLine(throw new Exception("Nor would this"));

          C#团队在有用的地方给了我们灵活性（通常，它允许你以更简洁的方式表达与以前完全相同的概念），但防止我们在上下文中使用荒谬的throw表达式而搬起石头砸自己的脚。

          我们的下一个特性继续了允许我们以更少的冗余表达相同逻辑的主题，通过简化默认运算符与默认字面量。

          默认字面量（C# 7.1）#

          default(T)运算符在C# 2.0中引入，主要用于泛型类型。例如，要从列表中检索值，如果索引在范围内，则返回值，否则返回该类型的默认值，你可以编写这样的方法：

          static T GetValueOrDefault<T>(IList<T> list, int index)
{
    return index >= 0 && index < list.Count ? list[index] : default(T);
}

          默认运算符的结果与当你让字段未初始化时观察到的类型的默认值相同：对于引用类型是空引用，对于所有数字类型是适当类型的零，对于char是U+0000，对于bool是false，对于其他值类型是所有字段设置为相应默认值的值。

          当C# 4引入可选参数时，指定参数默认值的一种方法是使用默认运算符。如果类型名称很长，这可能很笨拙，因为你最终在参数类型及其默认值中都出现了类型名称。这方面最糟糕的违规者之一是CancellationToken，特别是因为该类型参数的常规名称是cancellationToken。一个常见的异步方法签名可能是这样的：

          public async Task<string> FetchValueAsync(
    string key,
    CancellationToken cancellationToken = default(CancellationToken))

          第二个参数声明如此之长，以至于需要一整行用于书籍格式化；它有64个字符。

          在C# 7.1中，在某些上下文中，你可以使用default而不是default(T)，并让编译器推断你想要的类型。尽管除了前面的例子之外，肯定还有其他好处，但我怀疑这是主要的动机之一。前面的例子可以变成这样：

          public async Task<string> FetchValueAsync(
    string key, CancellationToken cancellationToken = default)

          这更简洁。没有后面的类型，default是一个字面量而不是运算符，它的工作方式类似于null字面量，除了它适用于所有类型。字面量本身没有类型，就像null字面量没有类型一样，但它可以转换为任何类型。该类型可能从其他地方推断，例如隐式类型数组：

          var intArray = new[] { default, 5 };
var stringArray = new[] { default, "text" };

          这段代码片段没有显式列出任何类型名称，但intArray隐式地是int[]（默认字面量被转换为0），而stringArray隐式地是string[]（默认字面量被转换为空引用）。就像null字面量一样，必须有一些类型来转换它；你不能只是要求编译器在没有信息的情况下推断类型：

          var invalid = default;
var alsoInvalid = new[] { default };

          如果默认字面量转换到的类型是引用类型或原始类型，则它被分类为常量表达式。这允许你在需要时在特性中使用它。

          需要注意的一个怪癖是，术语default有多种含义。它可以表示类型的默认值，也可以表示可选参数的默认值。默认字面量总是引用适当类型的默认值。如果你将它用作具有不同默认值的可选参数的参数，这可能会导致一些混淆。考虑清单14.11。

          清单14.11 指定默认字面量作为方法参数

          static void PrintValue(int value = 10)
{
    Console.WriteLine(value);
}

static void Main()
{
    PrintValue(default);
}

          参数的默认值是10 方法参数是int的默认值

          这将打印0，因为这是int的默认值。语言完全一致，但这段代码可能会引起混淆，因为default有不同的可能含义。我会尽量避免在这种情况下使用默认字面量。

          非末尾命名参数（C# 7.2）#

          可选参数和命名参数在C# 4中作为互补特性引入，并且两者都有顺序要求：可选参数必须在所有必需参数（除了参数数组）之后，命名参数必须在所有位置参数之后。可选参数没有改变，但C#团队注意到，通常命名参数作为提高清晰度的工具可能很有用，即使对于参数列表中间的参数也是如此。当参数是字面量（通常是数字、布尔值、字面量或null）且上下文没有阐明值的用途时，尤其如此。

          例如，我最近一直在为BigQuery客户端库编写示例。当你将CSV文件上传到BigQuery时，你可以指定一个架构，让服务器确定架构，或者如果表已存在，则从表中获取。在编写自动检测的示例时，我想明确你可以为模式参数传递空引用。以最简单但不清晰的形式编写，根本不清楚空参数的含义：

          client.UploadCsv(table, null, csvData, options);

          在C# 7.2之前，我使其更清晰的选项是：要么对最后三个参数使用命名参数，这最终看起来有点尴尬，要么使用解释性局部变量：

          TableSchema schema = null;
client.UploadCsv(table, schema, csvData, options);

          这更清晰，但仍然不理想。C# 7.2允许命名参数在参数列表中的任何位置，因此我可以在没有任何额外语句的情况下明确第二个参数的含义：

          client.UploadCsv(table, schema: null, csvData, options);

          这也可以帮助在某些情况下区分重载，其中参数（通常是null）可以转换为多个重载中的相同参数位置。

          非末尾命名参数的规则被精心设计，以避免任何后续的位置参数变得模糊：如果在命名参数之后有任何未命名参数，命名参数必须对应于与它如果是简单位置参数相同的参数。例如，考虑这个方法声明和三个调用：

          void M(int x, int y, int z){}

M(5, z: 15, y: 10);  // 有效：末尾命名参数乱序
M(5, y: 10, 15);     // 有效：非末尾命名参数顺序正确
M(y: 10, 5, 15);     // 无效：非末尾命名参数乱序

          第一个调用是有效的，因为它由一个位置参数后跟两个命名参数组成；很明显，位置参数对应于参数x，其他两个是命名的。没有歧义。

          第二个调用是有效的，因为尽管有一个命名参数后面有位置参数，但命名参数对应于如果它是位置参数时相同的参数（y）。同样，很清楚每个参数应该取什么值。

          第三个调用是无效的：第一个参数是命名的，但对应于第二个参数（y）。第二个参数应该对应于第一个参数（x），因为它是第一个非命名参数吗？尽管规则可以这样工作，但这一切变得有点混乱；当可选参数介入时更糟。禁止它更简单，所以语言团队决定这样做。

          下一个是一个在CLR中一直存在但直到C# 7.2才暴露的特性。

          C# 7引入的这些小特性虽不惊天动地，却共同提升了代码的简洁性和表达力。out变量允许在调用处声明变量，减少了不必要的先行声明，使代码更紧凑。数字字面量的改进（二进制字面量和下划线分隔符）增强了代码的可读性，特别是在处理位操作或大数字时。throw表达式使得在表达式上下文中抛出异常成为可能，简化了某些模式（如空值检查）。默认字面量减少了泛型和可选参数中default(T)的冗余类型书写。非末尾命名参数提高了代码的清晰度，允许在任何位置使用命名参数来阐明意图。这些特性都体现了C#语言设计中的实用主义：在不增加复杂性的前提下，为常见编码痛点提供优雅的解决方案，让开发者能更专注于业务逻辑而非语法细节。

          私有受保护访问权限（C# 7.2）#

          几年前，私有受保护（private protected）原本打算成为C# 6的一部分（也许他们计划甚至更早引入）。问题在于命名。当团队到达7.2版本时，他们决定找不到比私有受保护更好的名称了。这种访问修饰符的组合比受保护（protected）或内部（internal）都更严格。只有位于同一程序集内且在成员声明的子类（或同一类型）中的代码才能访问私有受保护成员。

          相比之下，受保护的内部（protected internal）比受保护或内部都更宽松。你可以从同一程序集中的代码，或从成员声明的子类（或同一类型）中的代码访问受保护的内部成员。

          关于这一点就这些；甚至不值得举例。从完整性角度来看，有这样一个访问级别很好，因为以前有一个可以在CLR中表达但不能在C#中表达的访问级别是很奇怪的。到目前为止，我只在自己的代码中使用过一次，并且我不期望将来会发现自己更多地使用它。我们将以一些不适合放在其他地方的其他零散内容结束本章。

          C# 7.3中的小改进#

          正如你在本章和本书前面所看到的，C#设计团队在发布C# 7.0后并没有停止对C# 7的工作。做了一些小的调整，主要是为了增强C# 7.0中发布的功能。在可能的情况下，我已经将这些细节包括在一般特性描述中。C# 7.3中的一些特性不符合这种方式，也不真正符合本章简洁代码的主题。但把它们漏掉感觉不对。

          泛型类型约束#

          当我在2.1.5节简要描述类型约束时，我遗漏了一些限制。在C# 7.3之前，类型约束不能指定类型参数必须派生自Enum或Delegate。这个限制已经解除，并且添加了一种新的约束：unmanaged约束。清单14.12给出了如何指定和使用这些约束的示例。

          清单14.12 C# 7.3中的新约束

          enum SampleEnum {}

static void EnumMethod<T>() where T : struct, Enum {}
static void DelegateMethod<T>() where T : Delegate {}
static void UnmanagedMethod<T>() where T : unmanaged {}

// 使用示例
EnumMethod<SampleEnum>();          // 有效：枚举值类型
EnumMethod<Enum>();                // 无效：不满足struct约束

DelegateMethod<Action>();          // 有效
DelegateMethod<Delegate>();        // 有效（不幸的是）
DelegateMethod<MulticastDelegate>(); // 有效

UnmanagedMethod<int>();            // 有效：System.Int32是非托管类型
UnmanagedMethod<string>();         // 无效：System.String是托管类型

          我展示了where T : struct, Enum作为枚举约束，因为这几乎总是你希望使用它的方式。这将T约束为真正的枚举类型：派生自Enum的值类型。struct约束排除了Enum类型本身。如果你试图编写一个适用于任何枚举类型的方法，你通常不希望处理Enum，它本身并不是真正的枚举类型。不幸的是，将这些约束添加到框架中的各种枚举解析方法上为时已晚。

          不幸的是，委托约束没有等效物。没有办法表达"只有使用委托声明声明的类型"的约束。你可以使用where T : MulticastDelegate的约束，但你仍然可以将MulticastDelegate本身用作类型参数。

          最后的约束是针对非托管类型的。我之前曾简要提到过这些，但非托管类型是一种不可为空、非泛型的值类型，其字段不是引用类型，递归地。框架中的大多数值类型（Int32、Double、Decimal、Guid）都是非托管类型。作为一个非非托管类型的值类型的例子，Noda Time中的ZonedDateTime不会是托管类型，因为它包含对DateTimeZone实例的引用。

          重载解析改进#

          围绕重载解析的规则已经被反复调整，通常以难以解释的方式进行，但C# 7.3中的变化是受欢迎的，并且相当简单。一些过去在重载解析完成后检查的条件现在更早检查。一些在早期版本的C#中被认为是模糊或无效的调用现在没问题。检查如下：

          • 泛型类型参数必须满足类型参数上的任何约束。
          • 静态方法不能像实例方法那样被调用。
          • 实例方法不能像静态方法那样被调用。

          作为第一个场景的例子，考虑这些重载：

          static void Method<T>(object x) where T : struct =>
    Console.WriteLine($"{typeof(T)} is a struct");  // 具有struct约束的方法

static void Method<T>(string x) where T : class =>
    Console.WriteLine($"{typeof(T)} is a reference type");  // 具有class约束的方法

// 调用
Method<int>("text");

          在以前的C#版本中，重载解析开始时将忽略类型参数约束。它会选择第二个重载，因为字符串是比对象更具体的常规参数类型，然后发现提供的类型参数（int）违反了类型约束。

          在C# 7.3中，代码编译时没有错误或歧义，因为类型约束在查找适用方法时被检查。其他检查类似；编译器比以前更早地丢弃对调用无效的方法。所有三种场景的示例都在可下载的源代码中。

          自动实现属性的后台字段特性#

          假设你想要一个由字段支持的简单属性，但你需要对字段应用一个特性以启用其他基础设施。在C# 7.3之前，你必须单独声明字段，然后使用样板代码编写一个简单的属性。例如，假设你想将一个DemoAttribute（只是我编造的一个特性）应用于支持字符串属性的字段。你需要这样的代码：

          [Demo]
private string name;

public string Name
{
    get { return name; }
    set { name = value; }
}

          当自动实现的属性几乎满足你想要的一切时，这很烦人。在C# 7.3中，你可以直接将字段特性指定给自动实现的属性：

          [field: Demo]
public string Name { get; set; }

          这不是特性的新修饰符，但以前在这个上下文中不可用。（至少不是官方的，也不在微软编译器中。Mono编译器已经允许它一段时间了。）这只是规范中语言不一致的另一个粗糙边缘，在C# 7.3中已经得到平滑处理。

          • 局部方法允许你清楚地表达特定代码片段是单个操作的实现细节，而不是在类型本身内普遍使用。
          • out变量纯粹是仪式性减少，允许将涉及多个语句（声明变量然后使用它）的一些情况减少为单个表达式。
          • 二进制字面量允许在需要表达整数值但位模式比数值更重要时提供更清晰的表达。
          • 当插入数字分隔符时，具有许多数字的字面量（可能容易使读者混淆）更清晰。
          • 与out变量一样，throw表达式通常允许将以前必须用多个语句表达的逻辑表示为单个表达式。
          • 默认字面量消除了冗余。它们还阻止你不得不重复说同样的事情。
          • 与其他特性不同，使用非末尾命名参数可能会增加源代码的大小，但一切都是为了清晰性。或者，如果你以前在只想命名中间一个参数时指定了许多命名参数，你将能够在保持可读性的情况下删除一些名称。

          本章涵盖了C# 7中的一系列小特性，它们共同提升了代码的简洁性和表达力。局部方法、out变量、数字字面量改进、throw表达式、默认字面量、非末尾命名参数以及私有受保护访问权限，这些特性虽不惊天动地，却在实际编码中提供了实实在在的便利。

          C# 7.3进一步增强了泛型约束（支持Enum、Delegate和unmanaged），优化了重载解析，并允许为自动实现属性的后台字段应用特性。这些改进体现了C#语言设计的实用主义：在不引入复杂性的前提下，解决开发者的实际痛点，完善语言细节，提升编码体验。

          这些特性共同推动了C#向着更现代、更表达力丰富的方向发展，使开发者能够以更少的代码表达更清晰的意图。
