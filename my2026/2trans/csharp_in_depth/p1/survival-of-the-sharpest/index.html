          本章内容包括

          1. C# 快速发展如何提升开发者的生产力
          2. 选择 C# 的小版本以使用最新功能
          3. 在更多环境中运行 C# 的能力
          4. 受益于开放且积极的社区
          5. 本书对新旧 C# 版本的关注点

          挑选出最有趣的 C# 特性来介绍并不容易。有些特性非常吸引人，但很少被使用；有些则极其重要，但对 C# 开发者来说已经司空见惯。像 async/await 这样的功能在很多方面都很出色，但很难简短地说明。话不多说，让我们来看看 C# 随时间的发展历程。

          一门发展中的语言#

          在本书的早期版本中，我曾提供过一个示例，展示该版本涵盖的语言演变过程。但现在，这种方式已难以做到既全面又有趣。虽然大型应用程序可能会使用几乎所有新特性，但任何适合印刷版展示的单一代码片段通常只会涵盖其中的一部分。

          因此，在本节中，我挑选了我认为最重要的 C# 语言演进主题，并简要展示了相关改进。这远非功能的详尽列表，也不是为了教你如何使用这些特性，而是提醒你已熟悉的功能如何推动了语言的发展，同时激发你对尚未接触的新特性的兴趣。

          如果你觉得其中一些特性借鉴了你熟悉的其他语言，几乎可以肯定你是对的。C# 团队毫不犹豫地吸收其他语言中的优秀理念，并将其重新塑造，使之自然融入 C#。这是一件非常棒的事情！特别值得一提的是，F# 对许多 C# 特性的设计灵感贡献良多。

          F# 可能最大的影响力不在于它为 F# 开发者带来了什么，而在于它对 C# 的影响。这并不是贬低 F# 作为一门语言本身的价值，也不是说不应该直接使用 F#。但目前，C# 社区远远大于 F# 社区，而 C# 社区应当感谢 F#，因为正是它激励了 C# 团队的发展。

          大规模与小规模下都实用的类型系统#

          C# 从一开始就是一门静态类型语言：你的代码需要指定变量、参数、方法返回值等的类型。你越能精确地描述代码所接受和返回的数据结构，编译器就越能帮你避免错误。 随着你构建的应用程序规模不断扩大，这一点尤为重要。如果你能在一屏内（或者至少能在脑海中一次性掌握）看到整个程序的所有代码，静态类型语言的优势并不明显。但随着规模的增长，代码能够简洁有效地传达其功能变得越来越关键。你可以通过文档来实现这一点，但静态类型则允许你以机器可读的方式进行沟通。
          随着 C# 的发展，其类型系统也支持了更细粒度的描述。最明显的例子就是泛型。在 C# 1.0 中，你可能会写出这样的代码：

          public class Bookshelf
{
	public IEnumerable Books { get { ... } }
}

          Books 序列中的每个元素是什么类型？类型系统并没有告诉你。使用 C# 2 的泛型，你可以更有效地表达：

          public class Bookshelf
{
	public IEnumerable<Book> Books { get { ... } }
}

          C# 2 引入了可空值类型，从而有效地表达信息的缺失，而无需使用诸如集合索引的 -1 或日期的DateTime.MinValue 之类的魔法值。

          C# 7 允许我们通过 readonly struct 声明告诉编译器用户自定义的结构体应当是不可变的。这个特性的主要目标可能是提升编译器生成代码的效率，但它在传达意图方面也有额外的好处。

          C# 8 的计划包括可空引用类型，这将带来更多的表达能力。到目前为止，语言中没有任何机制可以表达一个引用（无论是作为返回值、参数还是局部变量）是否可能为 null。如果不小心，这会导致容易出错的代码；如果小心，则需要大量样板验证代码，这两者都不理想。C# 8 将假设任何未显式标记为可空的引用类型都是非空的。例如，考虑如下方法声明：

          string Method(string x, string? y)

          参数类型表明，与 x 对应的参数不应为 null，而与 y 对应的参数则可以为 null。返回类型则表明该方法不会返回 null。

          C# 中对类型系统的其他改动规模较小，更多关注于单个方法的实现方式，而非大型系统中不同组件之间的关系。C# 3 引入了匿名类型和隐式类型局部变量（var）。这些特性有助于解决某些静态类型语言的缺点——冗长。如果你只在某个方法内部需要特定的数据结构，而在其他地方用不到，为了这个方法专门创建一个完整的类型显得过于繁琐。匿名类型允许你简洁地表达该数据结构，同时不失静态类型的优势：

          var book = new { Title = "Lost in the Snow", Author = "Holly Webb" };
string title = book.Title;
string author = book.Author;

          Name and type are still checked by the compiler

          匿名类型主要用于 LINQ 查询中，但为单个方法创建类型的原则并不依赖于 LINQ。同样，对于在同一语句中通过调用该类型的构造函数初始化的变量，显式指定其类型似乎有些多余。以下哪种声明方式更简洁，我心里有数：

          Dictionary<string, string> map1 = new Dictionary<string, string>();
var map2 = new Dictionary<string, string>();

          虽然在使用匿名类型时隐式类型推断是必要的，但我发现它在处理常规类型时也越来越有用。区分隐式类型推断和动态类型非常重要。前面提到的map2变量仍然是静态类型的，只是你不需要显式地写出类型。

          匿名类型仅在单个代码块内有用；例如，你不能将它们用作方法参数或返回类型。C# 7 引入了元组：一种值类型，实际上用于将多个变量组合在一起。框架对这些元组的支持相对简单，但额外的语言支持允许为元组的元素命名。例如，取代前面提到的匿名类型，你可以使用如下方式：

          var book = (title: "Lost in the Snow", author: "Holly Webb");
Console.WriteLine(book.title);

          元组在某些情况下可以替代匿名类型，但绝不是全部。它们的一个优点是可以用作方法的参数和返回类型。目前，我建议将元组限制在程序的内部 API 中使用，而不要公开暴露，因为元组只是简单地组合了多个值，而没有对它们进行封装。这也是我认为元组更多地是在实现层面简化代码，而不是提升整体程序设计的原因。

          另外，我还想提一下可能会在 C# 8 中引入的一个特性：记录类型。我把它们在某种程度上看作是“具名匿名类型”，至少在最简单的形式下是这样。它们既能带来匿名类型减少样板代码的好处，又能像普通类一样赋予这些类型额外的行为。敬请期待！

          代码愈发简洁#

          **C# 新特性的一个反复出现的主题，就是让你能够用越来越简洁的方式表达你的想法。**类型系统是其中的一部分，正如你在匿名类型中所见，但还有许多其他特性也对此有所贡献。你可能会听到很多相关的说法，尤其是关于新特性如何让你省去许多冗余代码。C# 的这些特性让你减少繁琐的仪式感，去除样板代码，避免冗余。这些说法其实都是在描述同一个效果。并不是说那些现在看来多余的代码本身有错，只是它们显得分散注意力且不必要。接下来，我们来看几个 C# 在这方面演进的例子。

          构造与初始化#

          首先，我们来看看如何创建和初始化对象。委托可能是演变最多且经历多个阶段的部分。在 C# 1 中，你必须为委托引用的方法单独写一个方法，然后以冗长的方式创建委托本身。举个例子，下面是在 C# 1 中为按钮的 Click 事件订阅一个新的事件处理器时所写的代码：

          button.Click += new EventHandler(HandleButtonClick);  //C# 1

          C# 2 引入了方法组转换和匿名方法。如果你想保留 HandleButtonClick 方法，那么方法组转换允许你将之前的代码改为：

          button.Click += HandleButtonClick;  // C# 2

          如果你的点击事件处理逻辑很简单，可能根本不需要单独定义一个方法，而是使用匿名方法：

          button.Click += delegate { MessageBox.Show("Clicked!"); }; // C# 2

          匿名方法还有一个额外优势，即可以充当闭包：它们能够使用其创建上下文中的局部变量。然而，在现代C#代码中，匿名方法并不常用，因为C# 3为我们提供了Lambda表达式。Lambda表达式几乎拥有匿名方法的所有优点，且语法更为简洁：

          button.Click += (sender, args) => MessageBox.Show("Clicked!"); // C# 3

          注意：此例中，Lambda表达式比匿名方法更长，因为匿名方法用到了一个Lambda表达式所不具备的特性：通过不提供参数列表来完全忽略参数。

          从C# 1的显式委托实例化，到C# 2的匿名方法，再到C# 3的Lambda表达式。每一次演进都让代码更聚焦于逻辑本身，而非语法结构。

          匿名方法与Lambda表达式在大多数情况下可互换，但存在一个微妙而重要的区别：匿名方法可以完全省略参数列表（使用 delegate { ... }），这意味着你可以在其中完全不使用事件参数；而Lambda表达式即使不使用参数，也必须显式声明参数列表（如 (sender, args) =>）。这在处理某些不需要参数的事件时，匿名方法能写出更短、意图更明确的代码。

          我之所以用事件处理程序作为委托的示例，是因为在 C# 1 中这是它们的主要用途。在 C# 的后续版本中，委托被应用于更多样化的场景，尤其是在 LINQ 中。

          LINQ 还通过对象初始化器和集合初始化器的形式，为对象初始化带来了其他好处。它们允许你在单个表达式内，指定要设置的新对象的一组属性，或要添加到新集合中的一组项。这用代码演示比描述更简单，我将借用第 3 章的一个例子。考虑一下你以前可能这样写的代码：

          var customer = new Customer();
customer.Name = "Jon";
customer.Address = "UK";

var item1 = new OrderItem();
item1.ItemId = "abcd123";
item1.Quantity = 1;

var item2 = new OrderItem();
item2.ItemId = "fghi456";
item2.Quantity = 2;

var order = new Order();
order.OrderId = "xyz";
order.Customer = customer;
order.Items.Add(item1);
order.Items.Add(item2);

          而 C# 3 引入的对象初始化器和集合初始化器让这一切清晰得多：

          var order = new Order
{
    OrderId = "xyz",
    Customer = new Customer { Name = "Jon", Address = "UK" },
    Items =
    {
        new OrderItem { ItemId = "abcd123", Quantity = 1 },
        new OrderItem { ItemId = "fghi456", Quantity = 2 }
    }
};

          我并非建议您详细阅读这两个例子；重要的是第二种形式相对于第一种的简洁性。

          方法与属性声明#

          最明显的简化示例之一就是自动实现的属性。该特性最初在 C# 3 中引入，并在后续版本中得到进一步改进。试想一个在 C# 1 中需要这样实现的属性：

          private string name;
public string Name
{
    get { return name; }
    set { name = value; }
}

          而使用自动实现的属性，只需一行即可完成：

          public string Name { get; set; }

          此外，C# 6 引入了表达式主体成员，进一步减少了冗余代码。假设你正在编写一个封装现有字符串集合的类，并且想要将类的 Count 和 GetEnumerator() 成员直接委托给该集合。在 C# 6 之前，你必须这样写：

          public int Count { get { return list.Count; } }
public IEnumerator<string> GetEnumerator()
{
    return list.GetEnumerator();
}

          这是一个典型的“仪式性”代码示例：语言过去要求大量语法，却收益甚微。在 C# 6 中，代码变得清晰得多。=> 语法（Lambda 表达式已在使用）被用来表示表达式主体成员：

          public int Count => list.Count;
public IEnumerator<string> GetEnumerator() => list.GetEnumerator();

          尽管使用表达式主体成员的价值是个人主观感受，但我惊讶于它们对我代码可读性带来的巨大提升。我非常喜欢这个特性！另一个我起初未料到会如此频繁使用的特性是字符串插值，这是 C# 中与字符串相关的改进之一。

          => 符号的复用（从Lambda表达式到表达式主体成员）体现了优秀语言设计的一致性原则。

          字符串插值（$“Hello, {name}”）不仅仅是 String.Format 的语法糖。它作为C# 6改善字符串处理的明星特性，其设计也深刻反映了语言演进的逻辑：将常见模式语言化，并提供编译时检查与优化。

          那么，一个有趣的问题是：如果字符串插值能如此优雅地处理运行时字符串，C# 后续版本是否提供了在编译时就进行字符串操作、验证甚至生成代码的能力？这正是 内插字符串处理程序 和 源生成器 大显身手的领域，它们将字符串的强大能力从运行时提升到了元编程和极致性能的新维度。

          字符串处理#

          C# 的字符串处理经历了三项重大改进：

          • C# 5 引入了调用方信息特性，它使得编译器能够自动填充方法名和文件名作为参数值。这对于诊断目的（无论是永久性日志记录还是临时性测试）非常有用。
          • C# 6 引入了 nameof 操作符，允许以支持重构的形式表示变量、类型、方法及其他成员的名称。
          • C# 6 还引入了插值字符串。这虽然不是全新的概念，但它极大地简化了包含动态值的字符串构建。

          为了简洁起见，我将只演示最后一点。构建包含变量、属性、方法调用结果等的字符串是相当常见的需求，可能用于日志记录、面向用户的错误信息（如果不需要本地化）、异常消息等场景。

          以下是我的 Noda Time 项目中的一个例子。用户可以尝试通过 ID 查找日历系统，如果该 ID 不存在，代码会抛出 KeyNotFoundException。在 C# 6 之前，代码可能看起来像这样：

          throw new KeyNotFoundException(
    "No calendar system for ID " + id + " exists");

          使用显式的字符串格式化，则看起来是这样：

          throw new KeyNotFoundException(
    string.Format("No calendar system for ID {0} exists", id));

          注意：有关 Noda Time 的信息，请参阅第 1.4.2 节。理解此示例无需了解该项目。 在 C# 6 中，借助插值字符串直接在字符串中嵌入 id 的值，代码变得更为简洁：

          throw new KeyNotFoundException($"No calendar system for ID {id} exists");

          这看起来可能没什么大不了的，但我现在很难想象没有字符串插值该如何工作。

          这些只是帮助提升代码信噪比的最显著特性。我本还可以展示 C# 6 中的 using static 指令和空条件运算符，以及 C# 7 中的模式匹配、解构和 out 变量。与其扩展本章来提及每个版本的每个特性，不如让我们转向一个更具革命性而非渐进性的特性：LINQ。

          使用 LINQ 进行简单的数据访问#

          如果你问 C# 开发者他们喜欢 C# 的什么，他们很可能会提到 LINQ。你已经看到了一些为 LINQ 奠定基础的特性，但最革命性的部分是查询表达式。看这段代码：

          var offers =
    from product in db.Products
    where product.SalePrice <= product.Price / 2
    orderby product.SalePrice
    select new {
        product.Id, product.Description,
        product.SalePrice, product.Price
    };

          这看起来完全不像老式的 C# 代码。想象一下穿越回 2007 年，把这段代码展示给一位使用 C# 2 的开发者，然后告诉他：这段代码不仅支持编译时检查和智能感知（IntelliSense），而且能生成高效的数据查询语句。哦，对了，同样的语法也能用于常规的内存集合。

          对进程外数据查询的支持是通过表达式树实现的。表达式树将代码表示为数据，LINQ 提供程序可以分析这些代码，并将其转换为 SQL 或其他查询语言。尽管这极其酷炫，但我个人很少直接使用它，因为我不常与 SQL 数据库打交道。然而，我经常处理内存集合，并且我一直在使用 LINQ，无论是通过查询表达式还是配合 Lambda 表达式的方法调用。

          LINQ 不仅仅为 C# 开发者提供了新工具；它鼓励我们以一种基于函数式编程的新方式来思考数据转换。这影响的远不止数据访问。LINQ 为采纳更多函数式思想提供了最初的动力，而许多 C# 开发者已经拥抱了这些思想并将其推向了更远。

          C# 4 在动态类型方面做出了革命性的改变，但我认为它影响到的开发者数量不及 LINQ。随后，C# 5 再次改变了游戏规则，这次是关于异步编程。

          LINQ 的强大源于其双重实现机制。对于 IEnumerable<T> 的内存集合，查询通过委托（Lambda）和方法链实现；对于 IQueryable<T>（如数据库），则通过表达式树将查询逻辑编译成数据，由提供程序（如 EF Core）在进程外（如数据库服务器）翻译并执行。这实现了“一次编写，多处运行”的抽象。

          LINQ 的成功，是函数式编程思想（如高阶函数、延迟计算、不可变性倾向）在主流面向对象语言中一次极为成功的“软着陆”。它不仅仅是一个库或语法糖，而是重塑了一代 C# 开发者处理数据、集合和流的思维方式，为后续引入更多函数式特性铺平了道路。

          LINQ 将声明式查询和编译时安全带到 C# 中，改变了我们处理数据的方式。那么，一个顺理成章的问题便是：如果这种声明式的、基于表达式的强大能力可以用于查询，那么 C# 能否将类似的范式应用于代码的其他复杂领域，比如并发控制、状态管理或 API 组合？

          事实上，这正是后续 C# 版本和生态系统探索的方向。异步流（IAsyncEnumerable） 将 LINQ 的声明式风格带入了异步世界；而更广泛的响应式扩展（Rx.NET） 则可以说是“事件流的 LINQ”。这些发展都表明，LINQ 所确立的声明式、组合式编程模型，其影响力早已超越了最初的数据访问范畴，成为构建现代、复杂、响应式系统的核心范式之一。

          异步编程#

          长期以来，在主流语言中实现异步编程一直很困难。一些更为小众的语言从一开始就将异步作为核心考量，而某些函数式语言则将其处理得相对简单，仅作为它们能妥善处理的众多特性之一。但 C# 5 通过通常被称为 async/await 的特性，为主流语言的异步编程带来了前所未有的清晰度。该特性围绕异步方法包含两个互补的部分：

          • 异步方法能轻松地生成一个代表异步操作的结果。此结果类型通常是 Task 或 Task<T>。
          • 异步方法使用 await 表达式来消费异步操作。如果方法尝试等待一个尚未完成的操作，该方法会异步地暂停，直到该操作完成后再继续。

          注意：更准确地说，我可以称它们为异步函数，因为匿名方法和 Lambda 表达式也可以是异步的。

          “异步操作”和“异步暂停”的具体含义正是复杂之处，我在此不打算详细解释。但最终结果是，你可以编写异步的代码，而它看起来却与你更熟悉的同步代码非常相似。它甚至能以一种自然的方式支持并发。举个例子，请看这个可能从 Windows 窗体事件处理程序调用的异步方法：

          private async Task UpdateStatus()
{
    Task<Weather> weatherTask = GetWeatherAsync();
    Task<EmailStatus> emailTask = GetEmailStatusAsync();
    // 同时启动两个操作

    Weather weather = await weatherTask;
    EmailStatus email = await emailTask;
    // 异步等待它们完成

    weatherLabel.Text = weather.Description;
    inboxLabel.Text = email.InboxCount.ToString();
    // 更新用户界面
}

          除了展示如何并发启动两个操作然后等待结果外，这段代码还演示了 async/await 如何理解同步上下文。尽管启动并等待了长时间运行的操作，你仍能更新用户界面（这只能在 UI 线程中完成）。在 async/await 出现之前，实现这一点既复杂又容易出错。

          我并不声称 async/await 是解决异步问题的银弹。它并没有神奇地消除这个领域固有的所有复杂性。相反，它通过移除了以往所需的大量样板代码，让你能够专注于异步编程中那些本质上就困难的方面。

          到目前为止，您看到的所有特性都旨在简化代码。我想提到的最后一方面则略有不同。

          async/await 将异步代码的表达简化到了接近同步代码的水平。这自然引出一个更深层次的问题：如果我们可以如此流畅地编排单个异步操作，那么对于多个随时间持续产生结果的异步操作流（例如实时数据推送、事件流），C# 是否也提供了同样优雅的声明式处理方式？

          答案是肯定的，这正是 异步流 所解决的领域。它将 async/await 的“拉取”模型与 IEnumerable<T> 的迭代模式相结合，创造了 IAsyncEnumerable<T>，让你能够使用熟悉的 await foreach 来消费异步数据流。这标志着C#的异步模型从处理“单一的未来结果”进化到了处理“连续的未来序列”，为构建现代实时和流式处理应用铺平了道路。

          效率与复杂性的平衡#

          我还记得最初接触 Java 的经历；那时它完全靠解释执行，速度慢得令人痛苦。一段时间后，可选的即时（JIT）编译器出现了，最终人们几乎理所当然地认为任何 Java 实现都应该是 JIT 编译的。让 Java 表现出色需要付出巨大的努力。如果这门语言当时失败了，这些努力就不会发生。但开发者们看到了潜力，并且已经感受到了比以往更高的开发效率。很多时候，开发与交付的速度可能比应用程序的运行速度更重要。

          C# 的情况略有不同。公共语言运行时（CLR）从一开始就相当高效。语言本身对与本地代码轻松互操作的支持，以及对使用指针的性能敏感型不安全代码的支持，也提供了帮助。C# 的性能持续提升。（我略带苦笑地注意到，微软现在正在引入分层 JIT 编译，这与 Java HotSpot JIT 编译器大致相似。）

          但不同的工作负载有不同的性能需求。正如你将在 1.2 节中看到的，C# 如今应用于种类惊人的平台，包括游戏和微服务，这两者都可能具有苛刻的性能要求。

          异步在某些情况下有助于解决性能问题，但 C# 7 显然是迄今为止对性能最敏感的一个版本。只读结构体以及大幅扩展的 ref 特性应用范围，有助于避免冗余的数据复制。现代框架中提供的 Span<T> 特性及其所支持的类似 ref 的结构体类型，减少了不必要的内存分配和垃圾回收。显然，期望在于，如果谨慎使用，这些技术将能够满足特定开发者的需求。

          我对这些特性略微感到一丝不安，因为它们对我来说仍然显得复杂。我无法像理解常规值参数那样清晰地推理一个使用 in 参数的方法，而且我确信还需要一段时间才能自如地掌握哪些事能用、哪些事不能用 ref 局部变量和 ref 返回来做。

          我希望这些特性能被适度使用。在能从中受益的场景下，它们会简化代码，并且无疑会受到维护这些代码的开发者的欢迎。我期待在个人项目中尝试这些特性，并更好地在提升的性能与增加的代码复杂性之间找到平衡。

          我不想过分强调这种谨慎的论调。我猜测 C# 团队做出了正确的选择来包含这些新特性，无论我在工作中会多用还是少用它们。我只是想指出，你不必仅仅因为某个特性存在就一定要使用它。要有意识地决定是否要选择复杂性。说到选择加入，C# 7 带来了一个新的元特性：自 C# 1 以来首次使用了次要版本号。

          作者敏锐地指出了高性能特性带来的核心矛盾：它们为了极致的性能（避免复制、减少分配），被迫引入了更复杂的语言概念（如ref语义、更严格的类型限制），这损害了代码的可读性、可推理性和安全性。这是一种典型的工程权衡。

          C# 7 的性能特性可以被视为对系统级编程的“有限度”探索，它打开了通往高性能世界的大门，但门槛较高。那么，一个自然的问题是：C# 的后续发展是继续沿着这条增加可控性但也增加复杂性的道路前进，还是能找到一种更优雅、更安全的方式来实现高性能？

          C# 后续版本给出了一些答案：record 结构体提供了更清晰的值语义模型；内存与管道 API 提供了处理二进制数据的高级抽象；而源生成器则尝试将部分运行时成本转移到编译时。

          高速演进：使用次版本号#

          C# 的版本号序列有些独特，并且由于许多开发者容易将框架版本与语言版本混淆（这种混淆可以理解），情况变得更复杂了。（例如，没有 C# 3.5。.NET Framework 3.0 发布时附带的是 C# 2，而 .NET 3.5 发布时附带的是 C# 3。）C# 1 有两个发布版本：C# 1.0 和 C# 1.2。从 C# 2 到 C# 6（含），都只有主版本，并且通常由新版本的 Visual Studio 提供支持。

          C# 7 打破了这一惯例：它发布了 C# 7.0、C# 7.1、C# 7.2 和 C# 7.3，所有这些版本在 Visual Studio 2017 中均可使用。我认为这种模式在 C# 8 中很可能会延续下去。其目标是允许新特性在用户反馈的推动下快速演进。C# 7.1 到 7.3 的大部分特性都是对 C# 7.0 引入特性的微调或扩展。

          语言特性的频繁变化可能会令人不安，尤其是在大型组织中。可能需要更改或升级大量基础设施，以确保完全支持新的语言版本。许多开发者学习和采用新特性的速度可能各不相同。至少，语言的更新频率超过你的习惯会让人感到些许不适。

          因此，C# 编译器默认使用其所支持的最新主版本中最早的那个次版本。如果你使用 C# 7 编译器且未指定任何语言版本，默认情况下它将限制你只能使用 C# 7.0。如果你想使用更高的次版本，则需要在项目文件中指定，并选择加入使用这些新特性。你有两种方式可以做到这一点（虽然效果相同）。一种是直接编辑项目文件，在 <PropertyGroup> 中添加一个 <LangVersion> 元素，如下所示：

          <PropertyGroup>
  ...
  <LangVersion>latest</LangVersion> <!-- 指定项目的语言版本 -->
</PropertyGroup>

          如果你不喜欢直接编辑项目文件，可以在 Visual Studio 中进入项目属性，选择“生成”选项卡，然后单击右下角的“高级”按钮。这将打开如图 1.1 所示的“高级生成设置”对话框，允许你选择希望使用的语言版本以及其他选项。

          对话框中的这个选项并非全新，但现在你比以往更可能用到它。可供选择的值如下：

          • default — 最新主版本的第一个发布版（即最早次版本）
          • latest — 最新版本
          • 特定的版本号 — 例如，7.0 或 7.3

          这不会改变你所运行的编译器版本；它改变的是你可用的语言特性集。如果你尝试使用目标版本中不可用的功能，编译器错误信息通常会说明该特性需要哪个版本。如果你尝试使用编译器完全未知的语言特性（例如，在 C# 6 编译器中尝试使用 C# 7 的特性），错误信息通常就不那么清晰了。

          自首次发布以来，C# 这门语言已经走过了很长的路。那么它所运行的平台呢？

          不断演进的平台#

          对于 .NET 开发者来说，过去几年是令人振奋的。当然也伴随着一定的困惑，因为微软和 .NET 社区都在适应一个更开放的开发模式所带来的影响。但众多参与者辛勤工作的整体成果是显著的。

          多年来，运行 C# 代码几乎总意味着在 Windows 上运行。通常要么是用 Windows 窗体或 Windows Presentation Foundation 编写的客户端应用，要么是用 ASP.NET 编写并可能运行在 Internet Information Server 后的服务端应用。虽然其他选择早已存在，特别是 Mono 项目有着丰富的历史，但 .NET 开发的主流仍然在 Windows 上。

          在我于 2018 年 6 月写下这些文字时，.NET 世界已截然不同。最显著的发展是 .NET Core，这是一个可移植、开源、由微软在多操作系统上提供全面支持并拥有现代化开发工具的运行时和框架。仅仅在几年前，这还是无法想象的。再加上 Visual Studio Code 这种可移植的开源 IDE，你便看到了一个蓬勃发展的 .NET 生态系统，开发者可以在各种本地平台上工作，然后部署到各种服务器平台上。

          如果过分关注 .NET Core 而忽略了当下 C# 运行的其他多种方式，那将是一个错误。Xamarin 提供了丰富的跨平台移动端体验。其 GUI 框架允许开发者在不同设备上创建在适当场景下相当一致、同时也能利用底层平台特性的用户界面。

          Unity 是世界上最受欢迎的游戏开发平台之一。凭借其定制的 Mono 运行时和提前编译技术，它可能给习惯了更传统运行时环境的 C# 开发者带来挑战。但对许多开发者来说，这是他们接触这门语言的第一或唯一体验。

          这些被广泛采用的平台远非 C# 运行的全部方式。我最近一直在研究 Try .NET 和 Blazor，它们提供了两种形式迥异的浏览器/C# 交互方式。

          Try .NET 允许用户在浏览器中编写代码（支持自动补全），然后构建并运行这些代码。对于几乎零门槛地试验 C# 来说，它非常棒。

          Blazor 是一个直接在浏览器中运行 Razor 页面的平台。这些页面并非由服务器渲染后显示在浏览器中，而是使用一个转换为 WebAssembly 的 Mono 运行时版本，让用户界面代码在浏览器内部运行。仅仅几年前，整个运行时通过浏览器中的 JavaScript 引擎（不仅在完整电脑上，甚至在手机上）执行中间语言 的想法对我来说是荒谬的。我很高兴其他开发者拥有更多的想象力。这一领域的许多创新，只有在一个比以往更加协作、更加开放的社区中才得以实现。

          不断发展的社区#

          我从 C# 1.0 时代起就参与 C# 社区，从未见过它像今天这样充满活力。在我开始使用 C# 时，它很大程度上被视为一种“企业级”编程语言，社区中相对缺乏趣味性和探索精神。在这样的背景下，与其他语言（包括同样被视为企业语言的 Java）相比，C# 的开源生态系统发展得相当缓慢。大约在 C# 3 时代，alt.NET 社区开始关注 .NET 开发的主流之外，这在某种意义上被视为一种对微软的背离。

          2010 年，NuGet（最初称为 NuPack）包管理器发布，它使得生成和使用类库（无论是商业的还是开源的）变得容易得多。尽管下载 zip 文件、将 DLL 复制到合适位置、然后添加引用的障碍听起来并不十分巨大，但每一个摩擦点都可能让开发者望而却步。

          注意：早于 NuGet 的其他包管理器也已出现，其中 Sebastien Lambla 开发的 OpenWrap 项目尤其具有影响力。

          时间快进到 2014 年，微软宣布其 Roslyn 编译器平台将在新成立的 .NET 基金会下开源。随后，以初始代号 Project K 宣布了 .NET Core；之后出现了 DNX，接着是如今已发布并稳定的 .NET Core 工具链。然后是 ASP.NET Core、Entity Framework Core 和 Visual Studio Code。真正在 GitHub 上活跃发展的产品名单还在不断增加。

          技术固然重要，但微软对开源的新拥抱对于一个健康的社区同样至关重要。第三方开源包蓬勃发展，包括对 Roslyn 的创新性使用以及 .NET Core 工具链内的集成，这些都让人感觉恰到好处。

          这一切都不是凭空发生的。云计算的兴起使得 .NET Core 对 .NET 生态系统的重要性远超以往；对 Linux 的支持不再是可选项。但也正是因为 .NET Core 的存在，如今将 ASP.NET Core 服务打包到 Docker 镜像中、用 Kubernetes 部署、并将其用作可能涉及多种语言的更大应用的一部分，已经不是什么特别的事了。多个社区间优秀思想的交叉融合一直存在，但如今比以往任何时候都更加强烈。

          你可以在浏览器中学习 C#。你可以在任何地方运行 C#。你可以在 Stack Overflow 和无数其他网站上提出关于 C# 的问题。你可以在 C# 团队的 GitHub 仓库中参与关于语言未来的讨论。它并非完美；为了让 C# 社区尽可能对所有人开放和友好，我们仍有集体的工作要做，但我们目前已经处在一个非常良好的位置。

          我愿意相信《C# in Depth》这本书在 C# 社区中也占有一席之地。那么，这本书本身是如何演变的呢？

          不断发展的一本书#

          您正在阅读《深入浅出C#》第四版。虽然这本书的发展速度没有跟上语言、平台或社区的变化步伐，但它依然在不断演进。本节将帮助您了解本书的内容涵盖。

          多层次的覆盖范围#

          《C# in Depth》第一版于2008年4月问世，巧合的是，那也正是我加入谷歌的时间。当时我意识到，许多开发者对 C# 1 相当熟悉，但他们是在实践中逐步学习 C# 2 和 C# 3 的，并没有扎实地掌握所有特性是如何有机结合在一起的。我旨在通过深入剖析语言来弥补这一差距，帮助读者不仅理解每个功能是什么，更理解其设计背后的原因。

          随着时间的推移，开发者的需求也在变化。在我看来，社区似乎已经通过耳濡目染（至少对于早期版本）更深入地理解了这门语言。虽然并非人人都能达到这种深度理解，但对于第四版，我希望把重点放在较新的版本上。我仍然认为按版本演进理解语言是有益的，但对 C# 2-4 的每个特性细节进行剖析的需求已经减少了。

          注意：按版本逐个学习语言并非初学者学习语言的最佳方式，但如果你想深入理解它，这种方式很有用。我不会用同样的结构来写一本面向 C# 初学者的书。

          我也不热衷于厚重的书。我不希望《C# in Depth》令人望而生畏、难以手持或难以书写。如果为 C# 2-4 保留 400 页的篇幅，感觉不太合适。因此，我压缩了对这些版本的覆盖。每一个特性都会被提及，并在我认为合适的地方深入探讨，但深度不如第三版。请将第四版的覆盖范围视为对你已知主题的回顾，并帮助你确定哪些主题需要参考第三版进行更深入的阅读。你可以在 www.manning.com/books/c-sharp-in-depth-fourth-edition 找到获取第三版电子版的链接。

          本书将更详细地涵盖 C# 5-7 版本。异步编程仍然是一个难以理解的主题，而第三版显然完全没有覆盖 C# 6 或 7。

          写作，就像软件工程一样，往往是一种权衡的艺术。我希望我在详述与简洁之间取得的平衡对你来说行之有效。

          使用 Noda Time 的示例#

          我在书中提供的大部分示例都是独立的。但为了更有力地展示某些特性的价值，最好能指出我在实际生产代码中使用它们的地方。大多数情况下，我使用 Noda Time 来达到这一目的。

          **Noda Time 是我在 2009 年启动的一个开源项目，旨在为 .NET 提供一个更好的日期和时间库。不过，它还有另一个次要目的：对我来说，它是一个极好的试验场项目。它帮助我磨练 API 设计技巧，了解更多关于性能和基准测试的知识，并测试新的 C# 特性。**当然，所有这些都不会对用户造成破坏。

          C# 的每个新版本都引入了我能在 Noda Time 中使用的特性，因此我认为在本书中将这些作为具体示例是合理的。所有代码都可以在 GitHub 上找到，这意味着你可以克隆它并自行实验。在示例中使用 Noda Time 的目的并不是为了说服你使用这个库，但如果这恰好产生了影响，我也不会反对。

          在本书的其余部分，当我提及 Noda Time 时，我将假定你明白我在说什么。就其作为示例的适用性而言，以下几点很重要：

          • 代码需要尽可能可读。如果一个语言特性能让我为可读性而重构，我会抓住这个机会。
          • Noda Time 遵循语义化版本控制，新的大版本很罕见。我会关注应用新语言特性时的向后兼容性。
          • 我没有具体的性能目标，因为 Noda Time 可以用于许多需求不同的场景。但我确实会关注性能，并乐于采纳能提高效率的特性，只要它们不会让代码变得复杂得多。

          术语选择#

          在本书中，我尽可能遵循官方的 C# 术语，但偶尔也会让表述的清晰度优先于绝对的精确性。例如，在讨论异步时，我经常提到“异步方法”，而同样的信息也适用于异步匿名函数。同样地，对象初始化器也适用于可访问的字段和属性，但在解释时，先提一次这点，然后仅提及属性会更简洁。

          有时，规范中的术语在更广泛的社区中很少使用。例如，规范中有 “函数成员” 这个概念。它指的是方法、属性、事件、索引器、用户定义的运算符、实例构造函数、静态构造函数或终结器。这是一个对任何可能包含可执行代码的类型成员的统称，在描述语言特性时很有用。但当你在查看自己的代码时，这个概念就没那么有用了，这也是为什么你可能从未听说过它。我尽量少用这类术语，但我认为，本着更贴近语言本身的精神，熟悉它们是有价值的。

          最后，有些概念并没有官方术语，但用简略的形式指代它们仍然很有用。我最常使用的一个可能是 “无法言说的名称”。这个术语由 Eric Lippert 创造，指的是编译器为实现迭代器块或 Lambda 表达式等功能而生成的标识符。该标识符对 CLR 有效，但在 C# 中无效；它是一个在语言内无法被“说出口”的名称，因此保证不会与你的代码发生冲突。

          总结

          我热爱 C#。它既令人感到舒适，又充满令人兴奋之处，我乐于见证它的未来发展。我希望本章已将这些兴奋之情传递给你一些。但这仅仅是一个开始。让我们不再耽搁，正式开始本书的核心内容。
