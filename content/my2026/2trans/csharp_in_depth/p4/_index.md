

C# 7 是自 C# 1 以来第一个拥有多个小版本发布的版本。共有四个版本：
*   C# 7.0 于 2017 年 3 月随 Visual Studio 2017 版本 15.0 发布
*   C# 7.1 于 2017 年 8 月随 Visual Studio 2017 版本 15.3 发布
*   C# 7.2 于 2017 年 12 月随 Visual Studio 2017 版本 15.5 发布
*   C# 7.3 于 2018 年 5 月随 Visual Studio 2017 版本 15.7 发布

大多数小版本发布都是对早期 C# 7.x 版本引入的新功能进行扩展，而不是引入全新的领域，尽管第 13 章将介绍的与 `ref` 相关的特性在 C# 7.2 中得到了极大扩展。

据我所知，目前没有 C# 7.4 版本的计划，尽管我不会完全排除这种可能性。拥有多个小版本似乎运行得相当不错，我预计 C# 8 也会有类似的发布周期。

C# 7 的内容比 C# 6 更多，因为其特性更为复杂。元组在编译器如何看待它们的类型与 CLR 使用的类型之间存在有趣的分离。局部方法的实现与 Lambda 表达式的实现相比较，让我很着迷。模式匹配理解起来相当简单，但要充分利用它则需要一定的思考。与 `ref` 相关的特性即使听起来简单，本质上也很复杂。（我说的就是你，`in` 参数。）

1. Visual Studio 2002 包含 C# 1.0，Visual Studio 2003 包含 C# 1.2。我不知道版本号为什么跳过了 1.1，也不清楚这两个版本之间有什么区别。

尽管我预计大多数开发者会发现大多数 C# 6 的特性每天都很有用，但您可能会发现 C# 7 的一些特性对您来说根本没用。我在代码中很少使用元组，因为我通常针对它们不可用的平台。我不太使用与 `ref` 相关的特性，因为我的编码环境并非它们特别有用之处。这并不妨碍它们是很好的特性；它们只是并非普遍适用。C# 7 的其他特性，如模式匹配、`throw` 表达式和数字字面量改进，更可能对所有开发者有用，但影响或许不如那些更有针对性的特性。

我提到这些只是为了设定预期。一如既往，当您阅读某个特性时，请考虑如何将其应用到自己的代码中。不要觉得必须使用它；用最短的代码使用最多的语言特性并不会得分。如果您发现目前某个特性对您没用，那也没关系。只需记住它在那里，以便日后您处于不同的环境时，知道有哪些可用选项。

同样重要的是，我要为第 15 章设定预期，该章节展望了 C# 的未来。该章节大部分内容演示了 C# 8 预览版中已经可用的特性，但不能保证所有这些特性都会在最终版本中发布，而且很可能还有我根本没有提到的其他特性。我希望您会觉得我写到的这些特性像我一样令人兴奋，并请持续关注 C# 团队的新预览版和博客文章。对于 C# 开发者来说，这是一个激动人心的时代，无论是就我们现有的东西而言，还是就光明的未来前景而言。



> 本部分前言勾勒了C# 7的重要演变：**发布模式**从大版本迭代转向更敏捷的“小步快跑”模式，这使语言能更快响应社区需求。同时，特性本身也呈现出新特点：**价值与分工更为明确**。诸如值元组、`ref`结构体等特性针对高性能计算、系统编程等特定场景，并非日常通用工具，而模式匹配、`throw`表达式等则普遍提升代码表现力。这标志着C#从提供“广泛适用”的语法糖，转向同时为**特定领域问题提供深度解决方案**。作者引导读者以务实心态看待：不必强迫使用所有特性，而应将其视为工具箱中的新选项，在合适场景选用。这种务实的演进思路，以及预告中对C# 8的展望，共同揭示了一个趋势：C#正朝着更强大、更专业化且持续快速迭代的方向发展，开发者需要主动适应这种节奏并选择性吸收新工具。
