# 一门发展中的语言

在本书的早期版本中，我曾提供过一个示例，展示该版本涵盖的语言演变过程。但现在，这种方式已难以做到既全面又有趣。虽然大型应用程序可能会使用几乎所有新特性，但任何适合印刷版展示的单一代码片段通常只会涵盖其中的一部分。

因此，在本节中，我挑选了我认为最重要的 C# 语言演进主题，并简要展示了相关改进。这远非功能的详尽列表，也不是为了教你如何使用这些特性，而是提醒你已熟悉的功能如何推动了语言的发展，同时激发你对尚未接触的新特性的兴趣。

如果你觉得其中一些特性借鉴了你熟悉的其他语言，几乎可以肯定你是对的。C# 团队毫不犹豫地吸收其他语言中的优秀理念，并将其重新塑造，使之自然融入 C#。这是一件非常棒的事情！特别值得一提的是，F# 对许多 C# 特性的设计灵感贡献良多。

> F# 可能最大的影响力不在于它为 F# 开发者带来了什么，而在于它对 C# 的影响。这并不是贬低 F# 作为一门语言本身的价值，也不是说不应该直接使用 F#。但目前，C# 社区远远大于 F# 社区，而 C# 社区应当感谢 F#，因为正是它激励了 C# 团队的发展。



## 大规模与小规模下都实用的类型系统  

C# 从一开始就是一门静态类型语言：你的代码需要指定变量、参数、方法返回值等的类型。你越能精确地描述代码所接受和返回的数据结构，编译器就越能帮你避免错误。 
随着你构建的应用程序规模不断扩大，这一点尤为重要。如果你能在一屏内（或者至少能在脑海中一次性掌握）看到整个程序的所有代码，静态类型语言的优势并不明显。但随着规模的增长，代码能够简洁有效地传达其功能变得越来越关键。你可以通过文档来实现这一点，但静态类型则允许你以机器可读的方式进行沟通。  
随着 C# 的发展，其类型系统也支持了更细粒度的描述。最明显的例子就是泛型。在 C# 1.0 中，你可能会写出这样的代码：

```c#
public class Bookshelf
{
	public IEnumerable Books { get { ... } }
}
```

Books 序列中的每个元素是什么类型？类型系统并没有告诉你。使用 C# 2 的泛型，你可以更有效地表达：

```c#
public class Bookshelf
{
	public IEnumerable<Book> Books { get { ... } }
}
```

C# 2 引入了可空值类型，从而有效地表达信息的缺失，而无需使用诸如集合索引的 `-1` 或日期的`DateTime.MinValue `之类的魔法值。

C# 7 允许我们通过 `readonly struct `声明告诉编译器用户自定义的结构体应当是不可变的。这个特性的主要目标可能是提升编译器生成代码的效率，但它在传达意图方面也有额外的好处。

C# 8 的计划包括可空引用类型，这将带来更多的表达能力。到目前为止，语言中没有任何机制可以表达一个引用（无论是作为返回值、参数还是局部变量）是否可能为 null。如果不小心，这会导致容易出错的代码；如果小心，则需要大量样板验证代码，这两者都不理想。C# 8 将假设任何未显式标记为可空的引用类型都是非空的。例如，考虑如下方法声明：

```c#
string Method(string x, string? y)
```

参数类型表明，与 x 对应的参数不应为 null，而与 y 对应的参数则可以为 null。返回类型则表明该方法不会返回 null。  

C# 中对类型系统的其他改动规模较小，更多关注于单个方法的实现方式，而非大型系统中不同组件之间的关系。C# 3 引入了匿名类型和隐式类型局部变量（var）。这些特性有助于解决某些静态类型语言的缺点——冗长。如果你只在某个方法内部需要特定的数据结构，而在其他地方用不到，为了这个方法专门创建一个完整的类型显得过于繁琐。匿名类型允许你简洁地表达该数据结构，同时不失静态类型的优势：
