挑选出最有趣的 C# 特性来介绍并不容易。有些特性非常吸引人，但很少被使用；有些则极其重要，但对 C# 开发者来说已经司空见惯。像 async/await 这样的功能在很多方面都很出色，但很难简短地说明。话不多说，让我们来看看 C# 随时间的发展历程。

# 一门发展中的语言

在本书的早期版本中，我曾提供过一个示例，展示该版本涵盖的语言演变过程。但现在，这种方式已难以做到既全面又有趣。虽然大型应用程序可能会使用几乎所有新特性，但任何适合印刷版展示的单一代码片段通常只会涵盖其中的一部分。

因此，在本节中，我挑选了我认为最重要的 C# 语言演进主题，并简要展示了相关改进。这远非功能的详尽列表，也不是为了教你如何使用这些特性，而是提醒你已熟悉的功能如何推动了语言的发展，同时激发你对尚未接触的新特性的兴趣。

如果你觉得其中一些特性借鉴了你熟悉的其他语言，几乎可以肯定你是对的。C# 团队毫不犹豫地吸收其他语言中的优秀理念，并将其重新塑造，使之自然融入 C#。这是一件非常棒的事情！特别值得一提的是，F# 对许多 C# 特性的设计灵感贡献良多。

> F# 可能最大的影响力不在于它为 F# 开发者带来了什么，而在于它对 C# 的影响。这并不是贬低 F# 作为一门语言本身的价值，也不是说不应该直接使用 F#。但目前，C# 社区远远大于 F# 社区，而 C# 社区应当感谢 F#，因为正是它激励了 C# 团队的发展。



## 大规模与小规模下都实用的类型系统  

C# 从一开始就是一门静态类型语言：你的代码需要指定变量、参数、方法返回值等的类型。你越能精确地描述代码所接受和返回的数据结构，编译器就越能帮你避免错误。 
随着你构建的应用程序规模不断扩大，这一点尤为重要。如果你能在一屏内（或者至少能在脑海中一次性掌握）看到整个程序的所有代码，静态类型语言的优势并不明显。但随着规模的增长，代码能够简洁有效地传达其功能变得越来越关键。你可以通过文档来实现这一点，但静态类型则允许你以机器可读的方式进行沟通。  
随着 C# 的发展，其类型系统也支持了更细粒度的描述。最明显的例子就是泛型。在 C# 1.0 中，你可能会写出这样的代码：

```c#
public class Bookshelf
{
	public IEnumerable Books { get { ... } }
}
```

Books 序列中的每个元素是什么类型？类型系统并没有告诉你。使用 C# 2 的泛型，你可以更有效地表达：

```c#
public class Bookshelf
{
	public IEnumerable<Book> Books { get { ... } }
}
```

C# 2 引入了可空值类型，从而有效地表达信息的缺失，而无需使用诸如集合索引的 `-1` 或日期的`DateTime.MinValue `之类的魔法值。

C# 7 允许我们通过 `readonly struct `声明告诉编译器用户自定义的结构体应当是不可变的。这个特性的主要目标可能是提升编译器生成代码的效率，但它在传达意图方面也有额外的好处。

C# 8 的计划包括可空引用类型，这将带来更多的表达能力。到目前为止，语言中没有任何机制可以表达一个引用（无论是作为返回值、参数还是局部变量）是否可能为 null。如果不小心，这会导致容易出错的代码；如果小心，则需要大量样板验证代码，这两者都不理想。C# 8 将假设任何未显式标记为可空的引用类型都是非空的。例如，考虑如下方法声明：

```c#
string Method(string x, string? y)
```

参数类型表明，与 x 对应的参数不应为 null，而与 y 对应的参数则可以为 null。返回类型则表明该方法不会返回 null。  

C# 中对类型系统的其他改动规模较小，更多关注于单个方法的实现方式，而非大型系统中不同组件之间的关系。C# 3 引入了匿名类型和隐式类型局部变量（var）。这些特性有助于解决某些静态类型语言的缺点——冗长。如果你只在某个方法内部需要特定的数据结构，而在其他地方用不到，为了这个方法专门创建一个完整的类型显得过于繁琐。匿名类型允许你简洁地表达该数据结构，同时不失静态类型的优势：

```
var book = new { Title = "Lost in the Snow", Author = "Holly Webb" };
string title = book.Title;
string author = book.Author;
```

> Name and type are still  checked by the compiler

匿名类型主要用于 LINQ 查询中，但为单个方法创建类型的原则并不依赖于 LINQ。同样，对于在同一语句中通过调用该类型的构造函数初始化的变量，显式指定其类型似乎有些多余。以下哪种声明方式更简洁，我心里有数：

```c#
Dictionary<string, string> map1 = new Dictionary<string, string>();
var map2 = new Dictionary<string, string>();
```

虽然在使用匿名类型时隐式类型推断是必要的，但我发现它在处理常规类型时也越来越有用。区分隐式类型推断和动态类型非常重要。前面提到的` map2 `变量仍然是静态类型的，只是你不需要显式地写出类型。

匿名类型仅在单个代码块内有用；例如，你不能将它们用作方法参数或返回类型。C# 7 引入了元组：一种值类型，实际上用于将多个变量组合在一起。框架对这些元组的支持相对简单，但额外的语言支持允许为元组的元素命名。例如，取代前面提到的匿名类型，你可以使用如下方式：

```c#
var book = (title: "Lost in the Snow", author: "Holly Webb");
Console.WriteLine(book.title);
```

元组在某些情况下可以替代匿名类型，但绝不是全部。它们的一个优点是可以用作方法的参数和返回类型。目前，我建议将元组限制在程序的内部 API 中使用，而不要公开暴露，因为元组只是简单地组合了多个值，而没有对它们进行封装。这也是我认为元组更多地是在实现层面简化代码，而不是提升整体程序设计的原因。

另外，我还想提一下可能会在 C# 8 中引入的一个特性：记录类型。我把它们在某种程度上看作是“具名匿名类型”，至少在最简单的形式下是这样。它们既能带来匿名类型减少样板代码的好处，又能像普通类一样赋予这些类型额外的行为。敬请期待！

## 代码愈发简洁  

**C# 新特性的一个反复出现的主题，就是让你能够用越来越简洁的方式表达你的想法。**类型系统是其中的一部分，正如你在匿名类型中所见，但还有许多其他特性也对此有所贡献。你可能会听到很多相关的说法，尤其是关于新特性如何让你省去许多冗余代码。C# 的这些特性让你减少繁琐的仪式感，去除样板代码，避免冗余。这些说法其实都是在描述同一个效果。并不是说那些现在看来多余的代码本身有错，只是它们显得分散注意力且不必要。接下来，我们来看几个 C# 在这方面演进的例子。  

#### 构造与初始化  

首先，我们来看看如何创建和初始化对象。委托可能是演变最多且经历多个阶段的部分。在 C# 1 中，你必须为委托引用的方法单独写一个方法，然后以冗长的方式创建委托本身。举个例子，下面是在 C# 1 中为按钮的 Click 事件订阅一个新的事件处理器时所写的代码：

```c#
button.Click += new EventHandler(HandleButtonClick);  //C# 1
```

C# 2 引入了**方法组转换**和**匿名方法**。如果你想保留 `HandleButtonClick` 方法，那么方法组转换允许你将之前的代码改为：

```c#
button.Click += HandleButtonClick;  // C# 2
```

如果你的点击事件处理逻辑很简单，可能根本不需要单独定义一个方法，而是使用**匿名方法**：

```c#
button.Click += delegate { MessageBox.Show("Clicked!"); }; // C# 2
```

匿名方法还有一个额外优势，即可以充当**闭包**：它们能够使用其创建上下文中的局部变量。然而，在现代C#代码中，匿名方法并不常用，因为C# 3为我们提供了**Lambda表达式**。Lambda表达式几乎拥有匿名方法的所有优点，且语法更为简洁：

```c#
button.Click += (sender, args) => MessageBox.Show("Clicked!"); // C# 3
```

**注意**：此例中，Lambda表达式比匿名方法更长，因为匿名方法用到了一个Lambda表达式所不具备的特性：**通过不提供参数列表来完全忽略参数**。

> 从C# 1的显式委托实例化，到C# 2的匿名方法，再到C# 3的Lambda表达式。每一次演进都让代码更聚焦于逻辑本身，而非语法结构。
>
> 匿名方法与Lambda表达式在大多数情况下可互换，但存在一个**微妙而重要的区别**：匿名方法可以完全省略参数列表（使用 `delegate { ... }`），这意味着你可以在其中完全不使用事件参数；而Lambda表达式即使不使用参数，也必须显式声明参数列表（如 `(sender, args) =>`）。这在处理某些不需要参数的事件时，匿名方法能写出更短、意图更明确的代码。

我之所以用事件处理程序作为委托的示例，是因为在 C# 1 中这是它们的主要用途。在 C# 的后续版本中，委托被应用于更多样化的场景，尤其是在 **LINQ** 中。

LINQ 还通过**对象初始化器**和**集合初始化器**的形式，为对象初始化带来了其他好处。它们允许你在单个表达式内，指定要设置的新对象的一组属性，或要添加到新集合中的一组项。这用代码演示比描述更简单，我将借用第 3 章的一个例子。考虑一下你以前可能这样写的代码：

```c#
var customer = new Customer();
customer.Name = "Jon";
customer.Address = "UK";

var item1 = new OrderItem();
item1.ItemId = "abcd123";
item1.Quantity = 1;

var item2 = new OrderItem();
item2.ItemId = "fghi456";
item2.Quantity = 2;

var order = new Order();
order.OrderId = "xyz";
order.Customer = customer;
order.Items.Add(item1);
order.Items.Add(item2);
```

而 C# 3 引入的对象初始化器和集合初始化器让这一切清晰得多：

```c#
var order = new Order
{
    OrderId = "xyz",
    Customer = new Customer { Name = "Jon", Address = "UK" },
    Items =
    {
        new OrderItem { ItemId = "abcd123", Quantity = 1 },
        new OrderItem { ItemId = "fghi456", Quantity = 2 }
    }
};
```

我并非建议您详细阅读这两个例子；重要的是第二种形式相对于第一种的**简洁性**。

#### 方法与属性声明

最明显的简化示例之一就是**自动实现的属性**。该特性最初在 C# 3 中引入，并在后续版本中得到进一步改进。试想一个在 C# 1 中需要这样实现的属性：

```c#
private string name;
public string Name
{
    get { return name; }
    set { name = value; }
}
```

而使用自动实现的属性，只需一行即可完成：

```c#
public string Name { get; set; }
```

此外，C# 6 引入了**表达式主体成员**，进一步减少了冗余代码。假设你正在编写一个封装现有字符串集合的类，并且想要将类的 `Count` 和 `GetEnumerator()` 成员直接委托给该集合。在 C# 6 之前，你必须这样写：

```c#
public int Count { get { return list.Count; } }
public IEnumerator<string> GetEnumerator()
{
    return list.GetEnumerator();
}
```

这是一个典型的“仪式性”代码示例：语言过去要求大量语法，却收益甚微。在 C# 6 中，代码变得清晰得多。`=>` 语法（Lambda 表达式已在使用）被用来表示表达式主体成员：

```c#
public int Count => list.Count;
public IEnumerator<string> GetEnumerator() => list.GetEnumerator();
```

尽管使用表达式主体成员的价值是个人主观感受，但我惊讶于它们对我代码可读性带来的巨大提升。我非常喜欢这个特性！另一个我起初未料到会如此频繁使用的特性是**字符串插值**，这是 C# 中与字符串相关的改进之一。

> `=>` 符号的复用（从Lambda表达式到表达式主体成员）体现了优秀语言设计的**一致性原则**。
>
> 字符串插值（`$“Hello, {name}”`）不仅仅是 `String.Format` 的语法糖。它作为C# 6改善字符串处理的明星特性，其设计也深刻反映了语言演进的逻辑：**将常见模式语言化，并提供编译时检查与优化**。
>
> 那么，一个有趣的问题是：如果字符串插值能如此优雅地处理运行时字符串，C# 后续版本是否提供了在**编译时**就进行字符串操作、验证甚至生成代码的能力？这正是 **内插字符串处理程序** 和 **源生成器** 大显身手的领域，它们将字符串的强大能力从运行时提升到了元编程和极致性能的新维度。



#### 字符串处理

C# 的字符串处理经历了三项重大改进：

- **C# 5** 引入了**调用方信息特性**，它使得编译器能够自动填充方法名和文件名作为参数值。这对于诊断目的（无论是永久性日志记录还是临时性测试）非常有用。
- **C# 6** 引入了 `nameof` 操作符，允许以支持重构的形式表示变量、类型、方法及其他成员的名称。
- **C# 6** 还引入了**插值字符串**。这虽然不是全新的概念，但它极大地简化了包含动态值的字符串构建。

为了简洁起见，我将只演示最后一点。构建包含变量、属性、方法调用结果等的字符串是相当常见的需求，可能用于日志记录、面向用户的错误信息（如果不需要本地化）、异常消息等场景。

以下是我的 Noda Time 项目中的一个例子。用户可以尝试通过 ID 查找日历系统，如果该 ID 不存在，代码会抛出 `KeyNotFoundException`。在 C# 6 之前，代码可能看起来像这样：

```c#
throw new KeyNotFoundException(
    "No calendar system for ID " + id + " exists");
```

使用显式的字符串格式化，则看起来是这样：

```c#
throw new KeyNotFoundException(
    string.Format("No calendar system for ID {0} exists", id));
```

**注意**：有关 Noda Time 的信息，请参阅第 1.4.2 节。理解此示例无需了解该项目。
在 C# 6 中，借助插值字符串直接在字符串中嵌入 `id` 的值，代码变得更为简洁：

```c#
throw new KeyNotFoundException($"No calendar system for ID {id} exists");
```

**这看起来可能没什么大不了的，但我现在很难想象没有字符串插值该如何工作。**

这些只是帮助提升代码**信噪比**的最显著特性。我本还可以展示 C# 6 中的 `using static` 指令和空条件运算符，以及 C# 7 中的模式匹配、解构和 `out` 变量。与其扩展本章来提及每个版本的每个特性，不如让我们转向一个更具革命性而非渐进性的特性：**LINQ**。

#### 使用 LINQ 进行简单的数据访问

如果你问 C# 开发者他们喜欢 C# 的什么，他们很可能会提到 **LINQ**。你已经看到了一些为 LINQ 奠定基础的特性，但最革命性的部分是**查询表达式**。看这段代码：

```c#
var offers =
    from product in db.Products
    where product.SalePrice <= product.Price / 2
    orderby product.SalePrice
    select new {
        product.Id, product.Description,
        product.SalePrice, product.Price
    };
```

这看起来完全不像老式的 C# 代码。想象一下穿越回 2007  年，把这段代码展示给一位使用 C# 2  的开发者，然后告诉他：这段代码不仅支持编译时检查和智能感知（IntelliSense），而且能生成高效的数据查询语句。哦，对了，同样的语法也能用于常规的内存集合。

对**进程外数据查询**的支持是通过**表达式树**实现的。表达式树将代码表示为数据，LINQ 提供程序可以分析这些代码，并将其转换为 SQL 或其他查询语言。尽管这极其酷炫，但我个人很少直接使用它，因为我不常与 SQL  数据库打交道。然而，我经常处理内存集合，并且我一直在使用 LINQ，无论是通过查询表达式还是配合 Lambda 表达式的方法调用。

LINQ 不仅仅为 C# 开发者提供了新工具；它鼓励我们以一种基于**函数式编程**的新方式来思考数据转换。这影响的远不止数据访问。LINQ 为采纳更多函数式思想提供了最初的动力，而许多 C# 开发者已经拥抱了这些思想并将其推向了更远。

C# 4 在动态类型方面做出了革命性的改变，但我认为它影响到的开发者数量不及 LINQ。随后，C# 5 再次改变了游戏规则，这次是关于**异步编程**。

> LINQ 的强大源于其**双重实现机制**。对于 `IEnumerable<T>` 的内存集合，查询通过委托（Lambda）和方法链实现；对于 `IQueryable<T>`（如数据库），则通过**表达式树**将查询逻辑编译成数据，由提供程序（如 EF Core）在进程外（如数据库服务器）翻译并执行。这实现了“一次编写，多处运行”的抽象。
>
> LINQ 的成功，是函数式编程思想（如高阶函数、延迟计算、不可变性倾向）在主流面向对象语言中一次极为成功的“软着陆”。它不仅仅是一个库或语法糖，而是**重塑了一代 C# 开发者处理数据、集合和流的思维方式**，为后续引入更多函数式特性铺平了道路。
>
> LINQ 将声明式查询和编译时安全带到 C# 中，改变了我们处理数据的方式。那么，一个顺理成章的问题便是：如果这种声明式的、基于表达式的强大能力可以用于查询，那么 C# 能否将类似的范式应用于代码的**其他复杂领域**，比如并发控制、状态管理或 API 组合？
>
> 事实上，这正是后续 C# 版本和生态系统探索的方向。**异步流（`IAsyncEnumerable`）** 将 LINQ 的声明式风格带入了异步世界；而更广泛的**响应式扩展（[Rx.NET](https://Rx.NET)）** 则可以说是“事件流的 LINQ”。这些发展都表明，LINQ 所确立的声明式、组合式编程模型，其影响力早已超越了最初的数据访问范畴，成为构建现代、复杂、响应式系统的核心范式之一。
